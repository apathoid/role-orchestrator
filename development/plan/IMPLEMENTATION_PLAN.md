# Полный план реализации

## Цель и исходное состояние

Создать работающий Role Orchestrator с нуля по `docs/`. Сейчас есть только спецификация. Нет необходимости сохранять чужие форматы, имена классов, workflow или поведение. План не является миграцией. Каждый кластер добавляет законченную часть и её регрессионную защиту.

Diagnostics и тесты вводятся в C00–C01 и наращиваются в каждом кластере; C11 не является первым шагом наблюдаемости.

## Единица выполнения

Шаг `Cxx.n` имеет конкретное изменение, проверку и выходной контракт. Выполнять по порядку. Если найдено новое необходимое низкоуровневое условие, исправить слой-владелец и добавить regression, затем продолжить. Не плодить второй механизм для обхода первого.

Для каждого шага:

1. Прочитать указанные документы и состояние предыдущего шага.
2. Реализовать минимальное целостное поведение без предположения о скрытых старых требованиях.
3. Добавить проверку наблюдаемого контракта/риска; тесты принадлежат `development/quality/`.
4. Проверить диагностические события и ресурсный cleanup на соответствующих ветвях.
5. Запустить узкие проверки, затем предусмотренный кластерный набор. Широкую повторную проверку делать после значимого изменения или выявленной ошибки.
6. Обновить STATUS и relevant acceptance rows фактическими evidence. При ошибке не переходить к зависимому шагу с ложной отметкой completed.

## Политика тестирования

Core: deterministic tests с fake clock/ports, без настоящих timers/sleep/LLM. Contract: один общий ProviderPort suite для mock, CLI и ACP doubles. Integration: реальные дочерние процессы и filesystem storage в tmp. End-to-end: обе пользовательские поверхности, многомодельность, restart/cancel. Native: конкретные установленные провайдеры/клиент с зафиксированными версиями.

Не писать тесты, зеркалящие private functions или порядок строк. Каждая важная проверка имеет исходное состояние, событие, ожидаемый observable outcome и forbidden side effect. Матрица `quality/ACCEPTANCE_MATRIX.md` задаёт требования, а не требование создать по отдельному файлу на каждую строку.

## Фиксированные решения и уточняемые детали

Фиксированы модельное владение семантикой, отсутствие VCS/изоляции/глобальной freshness, один coordinator, ProviderPort, single-writer snapshot store, TypeScript ESM, отдельный harness и публичные поверхности. Не требуют переизобретения агентом.

При C00/C07/C08 неизбежно проверить доступную Node LTS, версии библиотек и реальные protocol fields/CLI flags. Это проверка внешних зависимостей по официальным источникам, не свобода менять архитектуру. Результат записать в development reports; только действительные поддерживаемые версии включить в продуктовые docs. Неподтверждённые флаги и SDK методы не выдумывать.

## Критерий полного завершения

Все C00–C12 выполнены, обязательные acceptance проверены, отсутствуют незакрытые подтверждённые существенные нарушения, product documentation соответствует коду, native readiness описана отдельно. Если доступа к реальным провайдерам нет, можно завершить implementation и локальные проверки, но общий статус остаётся `NATIVE ACCEPTANCE PENDING`, а не «готово к эксплуатации».

После реализации набор development можно удалить из поставки без изменения product code/docs/config. Для дальнейшего сопровождения рекомендуется сохранить regression harness в репозитории.
