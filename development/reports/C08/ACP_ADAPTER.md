# C08.2–C08.8 — Generic ACP ProviderPort

Linux x86-64, Node 24.22.1, ACP v1, `@agentclientprotocol/sdk` 2.4.0. Точные методы и источники приведены в [карте протокола](ACP_V1_PROTOCOL_MAPPING.md).

| Шаг | Реализация и наблюдение |
|---|---|
| C08.2 | `createAcpProvider` владеет одной Linux-группой процессов и одной нативной сессией на вызов. Локальный handle, attempt и ACP session ID имеют разные области действия. Fixture проверяет несовместимую версию, ранний выход, гонку вызовов, новое подключение и согласованное закрытие сессии. |
| C08.3 | Адаптер передаёт текст и явно предоставленные вложения. Изображение и embedded resource требуют заявленной возможности агента. Controller получает полный JSON Decision, Worker — текст. Контракты проверяют чужие и поздние обновления, повторы tool events, потерю транспорта и ограничение входящих кадров и накопленного вывода в 1 МиБ. Лимит накопления проверяется несколькими кадрами ниже покадрового лимита. |
| C08.4 | Брокер получает исходные option IDs, названия, allow/deny и once/always. Запрос привязан к попытке через broker binding, а к нативному запросу через пару session ID и RPC request ID. Проверены allow, deny, неизвестный ID, три параллельных запроса, поздний ответ и disconnect. Действующие standing decisions остаются в Host broker. |
| C08.5 | Клиентские файловые и terminal RPC перенаправляются только в явно переданные обработчики с authority, operation, attempt и сигналом отмены. Terminal объявляется только при наличии всех пяти обработчиков. Fixture проверяет успешную передачу файлового RPC, ошибку при отсутствии bridge и отмену вызова в bridge. |
| C08.6 | Идентификатор модели сверяется с ACP model select option. Смена подтверждается результатом `session/set_config_option`. Явно настроенный `nativeSettings.mode` сверяется с доступными session modes. Проверены точный выбор модели, отсутствие модели или подтверждения, поддерживаемый и неподдерживаемый режим. |
| C08.7 | Адаптер отправляет `session/cancel`, даёт агенту 300 мс на ответ и закрывает собственный процесс, если ответа нет. Поздний ответ сохраняется как наблюдение без применения Decision. Потеря транспорта после отправки оставляет эффект неизвестным. Fixture различает отмену от агента и от клиента, malformed terminal, выход до ответа и отмену ожидающих разрешений. |
| C08.8 | Общий ProviderPort suite, ACP fixture suite и сквозной путь Controller прошли. A18 и A20 имеют локальные контрактные доказательства. Нативные части A20 и A38 остаются UNVERIFIED. |

Одна нативная сессия на попытку позволяет однозначно привязать события ACP к вызову. В каталоге `session.resume`, `attempt.status` и `context.retrieval` объявлены `unsupported`. Восстановление операции через Host использует сохранённое состояние. Доставка retrieval через реальные адаптеры запланирована в C09.6. Per-turn usage остаётся unknown.

## Нативная проба

Установленный Codex ACP 2.5.0 ответил на `initialize` версией ACP v1, объявил image, embedded context и session close. Прямой вызов SDK `session/new` истёк через 12 секунд. Отдельная попытка через `createAcpProvider` с временным рабочим каталогом, профилем `gpt-6.1-sol` и 30-секундным дедлайном завершилась `DEADLINE_EXCEEDED` с `dispatchCertainty: not_sent`. Обе пробы использовали обычный stdio, а их процессы были закрыты. Причина задержки агента не установлена. Успешный prompt, фактическая модель, инструменты, разрешения, отмена и продолжение реальной сессии остаются UNVERIFIED. Внешний ACP-клиент и Zed входят в последующую приёмку C10/C12.
