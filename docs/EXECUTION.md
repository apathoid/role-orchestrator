# Модельное исполнение

## Контекст Controller

Controller получает буквальный запрос, доступные приложения, текущие ограничения пользователя, доступный каталог профилей/ролей/tools/skills, оставшиеся ресурсы, последние результаты и ссылки на историю. Инструкция сообщает: можно ответить сразу; делегировать только при ожидаемой пользе; самостоятельно проверить нужные свойства среды; не считать предыдущие выводы текущей истиной; изменять стратегию при новой информации.

Host не просит обязательную классификацию `investigate/review/change`. Такие слова допустимы в задаче и инструкциях. Выбор «сложности» — модельная оценка для распределения ресурсов, не обязательное числовое поле и не переключатель workflow.

## Основные сценарии

### Прямой ответ

1. Запрос сохранён; Controller вызван с контекстом.
2. Модель отвечает без делегирования, если информации достаточно.
3. Host сохраняет результат и доставляет его клиенту. Никакого обязательного review или VCS discovery.

### Исследование без изменения исходников

1. Модель интерпретирует запрет исправления как ограничение задачи и передаёт его специалисту при необходимости.
2. Исполнитель использует доступные инструменты в своей обычной среде. Может обнаружить, что нужный запуск пишет временные файлы; согласование определяется действующей пользовательской/провайдерской политикой.
3. Нет автоматического перевода в Host read-only sandbox. Если пользователь требует техническую гарантию, доступность её выясняется по конкретному native enforcement contract, а не названию роли.
4. Модель связывает вывод с фактическими observations и сообщает ограничения.

### Работа с VCS

1. Пользователь просит анализ пяти коммитов или иной истории.
2. Модель/исполнитель выясняет доступную VCS, наличие истории и смысл выбранного диапазона.
3. Если данных недостаточно, уточняет диапазон/контекст либо сообщает ограничение. Orchestrator не запускает `git init`, `status`, `rev-parse` или обход `.git` перед началом.
4. Идентичность выбранных объектов может попасть в observations как необязательные метаданные. Смена checkout не превращает их автоматически в invalid.

### Изменение с проверкой

1. Модель формулирует намерение и использует действующие разрешения пользователя/провайдера; Host не требует второго подтверждения уже предоставленного scope.
2. Исполнитель меняет файлы своими средствами. Конкурентные правки обрабатываются им в рамках обычной работы.
3. Модель выбирает проверку, специалиста или дополнительное исследование. Обязательная пользовательская проверка остаётся видимым требованием.
4. Неудача теста может привести к исследованию причины, fix или частичному итогу; Host не назначает маршрут Reviewer -> Fix по коду завершения.
5. Assessment отдельно отражает сделанные изменения, наблюдавшиеся проверки, вывод и неопределённости.

### Несколько моделей

1. Controller выбирает независимые подзадачи и соответствующие профили; формирует handoffs.
2. Coordinator запускает доступные actions в пределах concurrency/resources и указанной зависимости.
3. При `next_completion` возвращает первый доступный результат и список остальных pending. Модель решает ждать, продолжить или отменить ненужное.
4. Разногласие двух исполнителей — контекст, а не majority vote. Controller может попросить различающую проверку, сузить гипотезу или сохранить неопределённость.
5. Следующая задача может снова требовать только один профиль. Состав агентов не фиксирован.

### Изменившаяся среда

1. Пользователь/скрипт меняет файлы, индекс, branch или проект в рабочей директории.
2. Сам по себе этот факт не вызывает никакой host transition.
3. Если инструмент сообщил конфликт, исчезнувший файл или другой контекст, адаптер передаёт observation. Необязательный `reportedContext` содержит сообщённые источником `location`, `version` или `reportedAt`. История сохраняет эти сведения рядом с временем приёма и provenance. Запись доступна Controller на следующем предусмотренном моделью ходе и специалисту по выбранной ссылке.
4. Модель выбирает re-read, новый путь, корректировку плана или уточнение. Изменение вне согласованных ресурсов регулируется доступным permission contract, а не проверкой «репозиторий тот же».

### Уточнение и ожидание пользователя

1. Controller сообщает конкретный вопрос и варианты при необходимости.
2. Operation waiting содержит questionId; активные actions либо продолжаются по явному решению, либо отменяются. Host не прерывает независимую работу по умолчанию.
3. Ответ с questionId добавляется в ту же историю; бюджет сохраняется. Дубликат доставки не создаёт новый ход.

### Прерывание и resume

1. Сохранить известные результаты и неопределённые attempts; не делать выводов из отсутствия diff.
2. На resume загрузить state, актуальные permissions/configuration и контекст; не выполнять VCS freshness check.
3. Если адаптер реально предоставляет status lookup по attempt id, можно получить факт без повторения операции.
4. Controller получает unknown явно и выбирает разрешённое продолжение. Автоматический повтор неизвестного effectful invocation запрещён.

## Acceptance

Controller оценивает каждое существенное требование: выполнено, частично, не подтверждено или невыполнимо в имеющихся условиях. Host валидирует существование ссылок и форму, но не семантическую полноту. Технически завершённый transport не является принятием результата пользователем.

Буквальный запрос и пользовательские ограничения, включая явно запрошенную проверку, доступны Controller на каждом ходе. В assessment модель указывает идентификатор требования, статус, ссылки и при необходимости краткое `reason`. Host проверяет авторство по профилю вызова, уникальность идентификаторов в assessment и существование ссылок. На продолжении незакрытые статусы из последней assessment передаются как модельный контекст со ссылкой на полную запись.

Повтор проверки не обязателен из-за возраста evidence. Но утверждение «проверка прошла после этой правки» требует соответствующего наблюдения и порядка. Когда таких данных нет, модель сообщает именно отсутствие подтверждения. Нельзя компенсировать пробел синтетическим PASS или обязательным числом reviewing agents.

## Адаптивный reasoning effort (реализовано в Host и adapters)

[Контракт выбора и продолжения](REASONING_EFFORT.md) добавляет выбор profile + унифицированный level для specialists и одноразовый выбор следующего effort Controller. Controller может сделать новый самостоятельный ход с прежними данными, без делегирования и обязательного внешнего события. Это явное модельное решение в том же loop, не автоматический polling.

Host не вводит специальные ограничения чередования levels; обычные ресурсы, cancel и recovery сохраняются. Неподдерживаемый effort собственного следующего вызова Controller показывается пользователю без скрытой смены уровня. Отсутствие подтверждения провайдером не означает неподдерживаемость. Контракты и simulated integrations реализованы и проверены CI; нативная проверка самостоятельного поведения конкретных моделей и Zed остаётся UNVERIFIED.

## Область интеграционной приёмки

Публичные API, CLI и внешний ACP host могут проходить один сквозной synthetic сценарий, включая прямой ответ, делегирование, отказ инструмента, отмену и восстановление. Такой PASS подтверждает Host/adapter lifecycle при указанном fixture; отдельный native тест должен проверить реальные версии двух независимых исполнителей, Zed session/new/load/resume, permission и работу вне Git. Отсутствие native доступа отмечается UNVERIFIED, а не заменяется fake tool log.

### Локальная техническая остановка Controller

Ошибка конкретного Controller invocation останавливает дальнейшие Controller calls до явного продолжения, но не отменяет уже принятые независимые Workers. В `waiting` допускаются только ранее принятые разрешённые actions при локальной причине, с действительными dependencies, authority, cancellation и budgets. Глобальные limits и ожидание вопроса не открывают новые reservations. FIFO применяется к технически готовым reservation requests, не выбирает семантическую стратегию и не прерывает выполняющийся invocation. Ресурс не освобождается до подтверждённого detach.


## C12R.9 — Controller после многих выполненных поручений

У Controller остаётся один обычный cycle, модель может завершить запрос сразу, создать независимые Actions либо `nextController.continue` с необязательным точечным `contextRequest`. Host не переигрывает Worker и не создаёт отдельного `history-worker`. Производная карта работ объясняет прошлые Action/Attempt/outcome refs даже когда полные отчёты не входят в inline prompt; чтение выбранных старых записей в следующей Controller invocation использует существующий ContextPort с проверкой authority. Доставленные данные не дают разрешения на новые эффекты. Provider-native средства доступны как прежде, независимо от Catalog skills.

Вся техническая компоновка bound by trusted budgets, но гарантии помещаемости user input, инструкции/каталог Host и внутренний native prompt независимы от optional context budget; отсутствие полного результата указывается, а не маскируется семантическим Host summary. Восстановление, отмена, поздний результат и неопределённый эффект сохраняют ранее действующие инварианты.
