# Effect-aware verification (P2)

The orchestrator normally treats a zero exit code as PASS and treats changes made by a verifier as checkout drift. **Do not globally change those defaults.** Some analyzers deliberately rewrite tracked JSON diagnostics and use a nonzero exit code both for improvements and for regressions. A host-owned declaration can enable deterministic domain assessment for **one configured command** without teaching the core about a specific npm script.

## Trusted configuration

Set `AGENT_VERIFY_COMMANDS` and `AGENT_VERIFY_POLICIES` in the environment of the orchestrator (for example through a trusted Nix/Home Manager service environment), not in agent output or project instructions:

```sh
export AGENT_VERIFY_COMMANDS='[["npm","run","check-agent-code-change"]]'
export AGENT_VERIFY_POLICIES='{
  "npm run check-agent-code-change": {
    "kind": "diagnostic_json_delta",
    "baseline": "pre_run",
    "acceptedExitCodes": [0, 1],
    "completion": { "path": ".verification-complete.json" },
    "reports": [
      {
        "path": "analyze-scripts/find-architecture-error/report/architecture/example.json",
        "itemsPath": "issues",
        "identityFields": ["rule", "file", "message", "severity"]
      }
    ]
  }
}'
```

**Replace the path, `itemsPath`, `identityFields`, and exit codes with the actual report schema and documented exit codes of the tool.** Choose a `baseline` that matches the analyzer's comparison contract: `pre_run` (default, compare previous report to newly written report) or `git_head` (compare the newly generated report against the same path in the checked-out commit). Do **not** enable `git_head` merely to suppress a failure: it is appropriate only if the analyzer actually treats committed reports as its authoritative baseline. The committed baseline must already contain each specified report; missing or malformed blobs remain unverified. This is an example, not a verified configuration for `check-agent-code-change` in another repository. Each `reports` entry describes an existing JSON file and an array of problems (`itemsPath` may be omitted if the document itself is an array). Field paths can be nested, e.g. `location.file`. Declare **all** report files the checker may modify (up to 48 entries per command). Do not omit fields that distinguish defects, such as category, contract, severity or location identity. Exclude volatile line/column numbers *only when they do not distinguish different problems*. Bad identity choices can mask regressions. The command must be included in the operator-configured verification suite to qualify for stage rechecks.

### Trusted completion contract for nonzero exits

An explicitly allowed **nonzero exit is not automatically successful**. Prior revisions trusted a changed JSON file or its timestamps; a crashed checker could therefore be accepted as a successful analysis. The host now requires a **fresh completion marker** before accepting any nonzero exit as a semantic improvement. If `completion` is omitted or invalid, nonzero is classified as inconclusive/failed, even when the comparison against `git_head` shows fewer issues. Ordinary `exitCode === 0` remains governed by the existing semantic regression checks.

An analyzer (or trusted wrapper) configured with `completion.path` must:

1. Read `AGENT_VERIFICATION_INVOCATION_ID` from its environment. This nonce is generated by the host for **every** execution. Never derive the nonce from persisted evidence or model output.
2. Run its entire analysis and finish writing every declared JSON report. Compute the SHA-256 digest of the **final bytes** of each report; report paths must match `reports[].path` exactly.
3. Only after successful completion, atomically publish a JSON file at `completion.path`, with this shape:

```json
{
  "invocationId": "<AGENT_VERIFICATION_INVOCATION_ID>",
  "status": "completed",
  "reportHashes": {
    "analyze-scripts/find-architecture-error/report/architecture/example.json": "<64-character SHA-256 hex>"
  }
}
```

This file should be **ignored by Git** and is a **diagnostic output**, not a source file. Create it using a temporary file followed by an atomic rename to avoid partial markers. The host checks the fresh nonce, marker contents, exact declared report set and observed hashes; symlinks and oversized markers are rejected. Markers from a previous execution cannot be reused. The analyzer must *not* publish success before any remaining failure-prone steps. A marker is a trusted completion declaration by the analyzer, not a proof that arbitrary untrusted code is correct; review its implementation carefully.

`AGENT_VERIFY_POLICIES` continues to belong to the operator. If an existing analyzer cannot emit a completion marker, a trusted wrapper must provide this protocol, or its nonzero results remain unverified. **Do not add the marker merely to silence the orchestrator.**

For durable/reusable evidence, independently configure `AGENT_VERIFY_INPUT_CLOSURES` with genuinely complete input dependencies. This is a separate contract: declaring report output files **does not** prove complete test inputs.

## Semantics

1. The host reads each declared report immediately before and after its own execution of the command. It compares multisets of issue identities, *not only their counts*. Movement of line numbers alone can be semantically unchanged.
2. New issues, even accompanied by removed issues or an exit code of `0`, mean **regressed** (TEST_FAILED). Only removals with no additions mean **improved**. No identity change means **unchanged**.
3. A nonzero exit code can mean PASS only when the operator has explicitly allowed that code and the baseline comparison shows improvement without newly introduced problems. Under `pre_run`, the issue sets must improve relative to the pre-invocation reports. Under `git_head`, they must improve relative to the pinned commit. In both cases a nonzero exit additionally requires the successful completion marker from **that very invocation**. An allowed nonzero code without a fresh marker is **inconclusive** (ENVIRONMENT_ERROR), not PASS; it could be an early crash.
4. During staged implementation, the checker may already have been invoked by coder before returning a `failed` check. The host reruns *only* commands from its configured suite that have a diagnostic policy and compares the final reports with the **pre-coder** reports. A nonzero rerun with unchanged reports may be accepted if the pre-coder comparison shows only improvement **and** the host observed a valid completion marker for that rerun. This does not bypass independent final verification.
5. Files changed during verification are treated as expected artifacts only if they match the actual declared report deltas and the checkout has no meaningful Git metadata change. Unknown paths, changed source code, stage/index changes and protected paths remain failures or require reconciliation. The check command must not write other files. The security policy still applies.
6. In read-only verification, writing reports is still a mutation. The orchestrator refuses execution of a declared effectful verifier before any check runs (including if its reports are Git-ignored). Use separate writable verification or a genuinely isolated environment instead. Targeted revalidation of a mutating checker cannot be silently treated as read-only.
7. The P2 Evidence Matrix only treats a host-observed, domain-accepted nonzero check as PASS in its *own* verification attempt. It still requires the review/acceptance binding, checkpoint and freshness constraints. A model's claim that a command passed cannot substitute for this.

**Final diff check:** `git diff --check` is deliberately run **after all configured verifier commands**. This verifies the end-of-attempt checkout rather than a pre-verification workspace. A diagnostic writer that introduces trailing whitespace now fails the mandatory suite. Targeted verification continues to include that same final diff check.

**Timeout/signal:** a command killed by timeout or signal never receives `PASS`, even if its SIGTERM handler exits with code 0. This also applies to preparation commands.

## Boundaries

- This is an **operator-declared policy**, never authorization inferred from generated model text or a repository README. A false or incomplete declaration can misclassify results: verify it against the actual analyzer contract.
- Before/after snapshots bound observable changes but do not prove sole authorship in the presence of concurrent processes. Unexpected mutations and Git drift remain subject to reconciliation.
- A report has to exist and be parseable before the run. For `git_head`, the committed baseline must also exist and be parseable. If either baseline is missing or ambiguous, the result is unknown. Initial report generation requires a deliberate baseline procedure, not automatic approval.
- A semantically different issue with the same projected identity cannot be detected. Choose fields sufficient for your analyzer; validate with negative scenarios.
- Static reports are not a substitute for independent runtime tests, current-run checks, or security enforcement. No unbounded automatic fix or retry is added.

## How to verify

Run `npm run test:evaluation` and check `verification-effects`, `verification-effects-stage` and `effect-aware-hardening`. They cover changed line numbers, improvements with nonzero exit status, balanced issue churn, newly introduced defects, unrelated source mutations, malformed reports, and real staged implementation continuation.
