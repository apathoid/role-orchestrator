# Продукт и функциональные требования

## Назначение

Role Orchestrator даёт пользователю единую задачу и историю исполнения при работе с несколькими доступными моделями/агентами. Польза нескольких исполнителей — специализация, независимое мнение, разделение объёма, выбор подходящих инструментов и стоимости. Количество исполнителей само по себе не является метрикой качества.

Обычный coding-агент остаётся владельцем своих инструментов. Orchestrator добавляет межвызовную координацию, выбор исполнителей моделью, передачу ограниченного релевантного контекста, управление ресурсами, наблюдаемость и сохранение прогресса. Он не требует специальных subagents какого-либо провайдера.

## Термины

| Термин | Значение |
|---|---|
| Host | Приложение, которое принимает запрос и выполняет инфраструктурные решения |
| Controller | Модель, выбирающая следующие действия и оценивающая результаты; Router/Planner — возможные обязанности этого же вызова |
| Provider | Внешний исполнитель/model service; adapter переводит его протокол в контракт ядра |
| Profile | Именованное назначение provider + model + параметры вызова |
| Role | Инструкция о цели/обязанностях исполнителя; не право и не стадия |
| Tool | Возможность конкретной операции, обычно принадлежащая провайдеру |
| Skill | Контекстная инструкция для выбранной задачи, без самостоятельного исполнения/выдачи прав |
| Plugin | Явно подключаемый доверенный код, регистрирующий предусмотренный тип расширения |
| Operation | Одно пользовательское поручение с продолжением, результатами и ресурсами |
| Attempt | Один dispatch к провайдеру с уникальной идентичностью и наблюдаемым исходом |
| Workspace context | Указанная среда/рабочая директория; не снимок файлов и не VCS-идентичность |
| Observation / finding | Полученное сообщение или наблюдение / вывод модели с основаниями |

## Обязательные требования

| ID | Наблюдаемое поведение |
|---|---|
| R01 | Принять запрос с текстом, приложениями/ссылками, workspace при необходимости; поддержать задачу без файлов |
| R02 | Controller может дать прямой ответ без обязательных Explorer/Planner/Reviewer вызовов |
| R03 | Controller выбирает роли, профили, инструменты, последовательность, параллельность и перепланирование |
| R04 | Delegation передаёт цель, критерии, ограничения и контекст; результат возвращается родительской операции |
| R05 | Зависимости действий исполняются корректно; нет повторного dispatch из-за дубликата сообщения |
| R06 | По мере результатов можно добавлять, отменять незапущенные действия и менять будущие назначения |
| R07 | Инструменты выбранного исполнителя доступны согласно настройкам пользователя/провайдера; нет автоматического sandbox по роли |
| R08 | User/provider permissions сохраняются; модель, skill и проектный конфиг не могут их расширять |
| R09 | Изменение workspace само по себе не вызывает остановку, re-review, потерю findings или сброс прогресса |
| R10 | Ядро запускается и восстанавливается без Git и без репозитория; VCS discovery делает исполнитель |
| R11 | Контекст хранит observations, модельные выводы, неопределённости и результаты с происхождением |
| R12 | Модель может переиспользовать/оспорить finding, запросить новые данные, сообщить частичный итог |
| R13 | Host не присваивает смысловой PASS на основании exit 0, числа агентов или заполненных полей |
| R14 | Отмена останавливает новые dispatch, передаётся активным исполнителям и сохраняет известные/неизвестные исходы |
| R15 | Restart восстанавливает контекст и расход; неизвестные эффекты не воспроизводятся автоматически |
| R16 | Лимиты учитывают весь operation, включая дочерние и неудачные вызовы; недоступные метрики помечаются unknown |
| R17 | Конфигурация валидируется до использования; профили и роли не содержат имён провайдеров в логике core |
| R18 | Generic ACP и CLI/headless adapters реализуют один порт; минимум два разных реальных исполнителя подтверждают переносимость |
| R19 | Внешний ACP Host поддерживает согласованные с клиентом сессии, prompt, progress, permission и cancel; CLI предоставляет тот же продуктовый смысл |
| R20 | Skills, provider plugins и tool extensions подключаются явно и не могут регистрировать обход core invariants |
| R21 | Диагностика объясняет каждый dispatch, ожидание, отказ, отмену и recovery конкретными id и причинами |
| R22 | Потеря диагностического sink не ломает исполнение; потеря обязательного durable commit не выдаётся за подтверждённый dispatch/result |
| R23 | Ресурсы процесса/сессии имеют владельца и cleanup; поздние события сохраняются без возобновления отменённой работы |
| R24 | SDK/protocol ошибки, permission denial, tool failure, модельная оценка и неизвестный исход различимы |
| R25 | Сборка/запуск/публичные docs независимы от удаляемого дерева разработки |
| R26 | Поведение сохраняется при нескольких operation; независимые задачи не блокируются из-за локальной проблемы одной |
| R27 | Пользователь видит профиль, существенный прогресс, ограничения и основание вывода; принятие пользователем отделено от оценки модели |
| R28 | Пользовательский ответ на уточнение продолжает ту же operation с сохранением расхода; новое поручение имеет новый id |

## Качество и исключения

Core MUST быть проверяем без внешней модели, сети, файлов проекта и установленной VCS. Это требование тестируемости, не имитация способности LLM рассуждать. Production transport MUST не подменять неизвестные результаты синтетическим успехом.

Не входят в продукт: собственная изоляция исполнения, гарантированная защита от произвольного кода того же пользователя, file locking/CAS исходников, Git consistency manager, автоматический rollback проекта, универсальный анализ опасности shell-команд, глобальная актуальность findings, обязательное множество агентов, миграция предыдущих систем.

Параметры контекстного объёма, параллельности, таймаутов и затрат конфигурируемы по реальным ресурсам. Число этапов и необходимость review не ограничиваются произвольной архитектурной квотой. Если пользователь требует конкретную проверку, отсутствие её подтверждения отражается в оценке требования; Host не придумывает обязательный маршрут для её получения.
