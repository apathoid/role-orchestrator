## 1. Purpose and evidence

Make useful RO-owned technical information accessible to the model at the point where it can use it. Improve informed independent model decisions, not the formal complexity of contracts, the number of mechanisms, or the Host's responsibility. The model owns task meaning, strategy, delegation, evidence relevance, correction choices and assessment. The Host provides accurate, sufficient and proportionate technical facts about its existing contracts, state, capabilities and failures. It may cheaply derive useful technical facts from information it already owns; it does not solve the task or search for a solution on the model's behalf.

Success is a more informative interface with substantially unchanged runtime architecture and behavior. Do not treat a full JSON Schema, an expanded universal FieldError, dynamic lists everywhere, smaller prompts or a particular runtime example as deliverables in themselves. Prefer retaining an already computed value, clarifying an existing response or description, or exposing an existing small set of facts over new infrastructure. When several solutions are sufficient, choose the smallest coherent one. Preserve model access to information even when different providers present schemas differently.

## 4. C22.1 — Informative technical errors (required F1/F2)

### 4.1 Static facts from actual contracts

Unknown-field errors should expose the supported input fields at that object level when directly known. The record(fields) owner already has them; reuse actual definitions rather than handwritten lists per erroneous name. Include ControllerIntent top-level checks and relevant nested Action, Assessment, Requirement, Finding, wait/dependency/continuation/contextRequest objects and RO tool arguments. Provide the relevant local set, not a full schema on every failure. Example (illustrative, not fixed new API):

- path: $.finalAssessment.requirements[0].name
- expected: a supported field
- allowedFields: requirementId, status, observationRefs, findingRefs, reason

Ensure the list describes the **external** contract. Intent normalization uses canonical Decision with technical placeholders; schemaVersion, decisionId, operationId, contextCursor, and Assessment/Finding author are Host-owned for Intent and must not be suggested as model fields; canonical Decision requires its existing fields. Intent omissions/defaulted arrays (including additions/cancellations, Action contextRefs/dependsOn, Finding supports/uncertainties, Assessment arrays and Requirement reference arrays) retain existing semantics. Do not add a second validator/decoder, new normalization behavior or path/field-name heuristics specific to examples. Preserve existing cross-field checks and explicit Host-owned omission advice. Use shared structural facts if useful for both diagnostics and input descriptions. Verify nested unknown fields and intentional differences with legacy Decision.

Inspect type/missing/enum/union/cross-field/ref diagnostics in affected contracts and clarify only confirmed gaps. Preserve already informative oneOf() values (e.g. complete | partial | unresolved; fulfilled | partial | unverified | unavailable). Preserve first-error behavior; no aggregate validation or second pass merely to generate diagnostics. Distinguish actual technical condition from all admissibility requirements. Do not return rejected input, secrets or arbitrary user data as suggestions.

### 4.2 Existing dynamic facts (conditional H1)

Where the rejecting owner already has useful small scoped sets, expose them if it can do so simply: e.g. supported levels of selected profile, registered/visible Catalog profile/role/Host-managed skill IDs, current operation identity, known proposal refs, existing terminal Action IDs or registered RO tool names. No requirement to cover every type of error, generate candidate lists or compute all legal solutions. Reuse already produced availableLevels or equivalent feedback. No scanning all profiles for capability suitability, no repeat admission, no probing provider, no history search for refs, no ranking or fallback choice. Report exactly what is known: allowed for the specific failed condition, known/registered in scope, or available at the check snapshot. Do not label mere existence as full admission or promise future availability. Empty or partial lists explicitly distinguished from unknown/unavailable; no partial list asserted exhaustive. For large or costly sets prefer precise scope/type and optional existing access route rather than enumeration. Do not reveal outside authority or alter failure category/outcome (CAPABILITY_UNAVAILABLE, PERMISSION_DENIED, RESOURCE_LIMIT etc. remain their own contracts).

### 4.3 Retain discarded retrieval diagnostics

The four own retrieval tools currently decode input then return only {kind:'unavailable', reason:'invalid_input'}. Return the already computed path and expected (and relevant bounded static details if available) through existing response without new validation. Preserve unavailable/invalid_input outcome and any existing transport error semantics. A retrieval input failure is not a Controller rejection and must not increment recovery counters. Exercise actual MCP wire responses, not just internal decoder. Do not change external tool contracts.

### 4.4 Representation, bounds and error identity

Prefer the simplest local representation sufficient for each path; do not require identical diagnostic shape across unrelated failures. The primary existing cause is mandatory; optional additional facts cannot block registration or replace the primary reason. In particular, decisionRecovery currently counts rejected Controller invocations (not each same-turn receipt) with signature [category, code, path, expected]. Preserve signature semantics and thresholds; dynamic allowed sets or omitted detail must not alter repeated-error identity. Preserve existing stable expected where correct; if a correction to wording is required, verify actual effects on historical/current recovery and report any intentional difference rather than silently altering limits or merging distinct failures. Optional detail separate from stable identity is preferred, not a mandated universal FieldError expansion.

Trace actual affected same-turn receipts, controllerDeclaration/ProviderPort, rejected journal event, persistence/reopen and correction context. If details are useful at a boundary where the error already persists, use minimal bounded representation compatible with existing records; no migration project, no new persistent diagnostic stream or rejected-body store. Avoid widening every Reason type to fit one caller. Keep actual code/path/category, scope, attribution and effect semantics. Existing provider reports untrusted. Check existing path/expected 512-character handling and actual MCP wire/control-receipt/serialized-byte bounds. Bounded details must not crowd out mandatory user data, cause whole response to be replaced by budget error, or change receipt/operation state. Handle large malicious keys/IDs, Unicode/JSON escaping, oversize or unavailable optional details, safe property handling (including unusual keys). No configurable budget solely for enrichment; use proportionate local bounds and existing limits. Bound before retaining control receipts or persisting data. Omitted diagnostics must leave the primary error intact and must not claim completeness.

Where feasible demonstrate via actual integration that additional schema information does not hide or alter previously observable replacements. Fixture tests prove only behavior on delivered requests, not a real client's validation or generation behavior.

RO cannot guarantee reception of events a provider never sends. Do not infer attempted replacements from reasoning, intercept provider internals, add model-specific contracts or require provider-side validation to be disabled. If a new restrictive representation reproducibly prevents or changes delivery of formerly observed invalid replacements, simplify/remove restrictive keywords or choose description-only representation; do not weaken finality or lineage guarantees to compensate.
