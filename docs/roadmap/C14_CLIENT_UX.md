## 0. Целевой UX и неизменяемые границы

Один пользовательский диалог с Controller; нативная коммуникация насколько её предоставляет конкретный provider/client; фактическая информация об orchestration, принятые findings и возможность ответить на interaction без ожидания окончания операции. CLI и графические ACP-клиенты используют одинаковые источники, но не обязаны выглядеть одинаково. Не создавать отдельный GUI application или web frontend, Zed extension, UI-specific protocol in core, custom ACP client requirement. Существующие внешние ACP clients работают с их native widgets, CLI — собственный thin renderer.

Сохранять все инварианты C13 и AGENTS.md. Presentation **не влияет** на invocation, model prompt, provider settings, context, Decision/Outcome, model autonomy, delegation, skills, evidence, workspace, grants, budget/scheduler/slot, cancellation или final assessment. Никаких обязательных сообщений/отчётов, streaming parser heuristics, aggregation thinking blocks, progress inference, host-written plan, status from keywords, hidden content relevance ranking, mandatory user intervention, OS/FS/host isolation, Git/source identity checks. Native thinking только фактически предоставленное и предназначенное для экспонирования; не извлекать скрытое рассуждение. Не писать reasoning в durable journal только ради UI; существующий session/load transcript contract сохраняется.

### Пример ожидаемого CLI (иллюстрация, не новый event contract)

```text
You: Проверь изменения и исправь подтверждённые ошибки.

Controller · started
Thinking …                       [native reasoning, если доступен]
Explorer · started
Reviewer · started
Explorer · completed             [фактический lifecycle]
Reviewer · finding               [accepted model finding, либо explicit live]
  Возможна потеря результата при отмене.
Thinking …                       [native chunks продолжаются]
Coder · started
Coder · permission
  [оригинальное действие и опции провайдера]
  1 Allow once   2 Deny            [только если предложены]
You: 1
Coder · completed
Controller:
  [финальный модельный ответ без повторения envelope]

Operation: finished · partial     [только реальный итог/assessment]
```

Не обещать именно такую хронологию или наличие каждого вида: Controller может ответить напрямую, выбрать иные роли, не создавать findings, запросить clarification, работать без reasoning. Не называть finished=успех. При отсутствии explicit public message channel не показывать ambiguous structured output и не утверждать live finding interleaving; принятая finding может поступить после Outcome. CLI default layout простое потоковое, не рисовать искусственные блоки thinking; графический клиент сам управляет группировкой.

## C14.1 — Общая минимальная presentation mapping

1. Reuse C13 Activity, Execution Events, authoritative inspect/terminal results; composition in hosts/application-facing consumer only. Общие pure formatting helpers только для реально общего атрибутивного текста; не превращать их в универсальный UI framework, renderer state machine, new model state.
2. Compact: исходный user message/final, native thinking (если доступно), краткие actual start/finish/wait/cancel/error notices с role/profile/attempt when needed to disambiguate, accepted model findings, permission/interaction/clarification actionable. Detailed adds actual native tools/updates, available model plan, IDs if needed, full offered action/choices. Debug adds safe technical refs, timings, status, correlation, delivery gaps and existing diagnostic metadata, not raw prompts/secrets. Если client не поддерживает конкретный display type — supported safe fallback или omission with limitation, не синтетический reasoning/tool_call.
3. Lifecycle: только существующие факты, e.g. attempt.started/terminal actual state; no grouping by time window, no invented "started 2 workers" unless event actually says it, no success/completeness inference. Отдельные события отдельных Workers. Gap notice from C13, no history reconstruction, explicit inspect may show current authoritative snapshot (not replay).
4. Identity: operation/attempt and native stream/resource where available; no stable native ID requirement; no merging across attempts, don't synthesize message boundaries; no re-chunking heuristics / thinking close/open state. Consumer may label native chunks without changing their contents; client decides layout. Same tool_call/update IDs or proven namespaced mapping per attempt; no fake tool calls. Only explicit findings, accepted record refs model provenance; preserve live vs accepted distinction, no text-derived severity.
5. User output dedup only by explicit existing source identity; final result rendered once via execution path, not text similarity. Keep partial/error/cancel/unknown notices faithful; no "completed successfully" from transport exit. Preserve user-facing message text, no host summary/rewrite. Sanitize terminal escapes/control chars for display without mutating durable/provider payload; no execution of links/markup. ACP protocol payloads use standard types, no raw debug secrets.
**Приёмка:** golden fixtures direct, two workers, same role different attempts, findings/live absence, partial/unknown, native plan absent/present, missing IDs, compact/detailed/debug equivalence of execution, gap and error, original actionable permissions. Golden tests validate meaning and identity, not exact spacing for all terminals.

## C14.2 — CLI renderer and live interaction

1. Integrate subscription with current CLI run/resume/owner execute path, before relevant execution starts; unsubscribe finally; renderer processes bounded delivery C13 independent of provider. Render incremental native chunks, lifecycle, accepted findings and final. No wait window to make text pretty, no renderer await in execution path. One stdout writer/multiplexing at Host display boundary (not execution scheduler), prevent prompt input corruption. Preserve existing final exit codes and machine output. TTY color/labels optional, respect no-color/terminal width; fallback plain text, no alternate screen/TUI dependency unless proven necessary.
2. Interactive input only when a real pending request exists. Display origin (Operation/Attempt/provider/role as available), original action/options and actual deadline/error, stable user-selectable request label derived from pending registry (not new authority). Permission original options, no invented always allow; native supported question/form through protocol-defined fields with minimal CLI adaptation, unsupported complex form -> addressable unavailable, no pretend response. Controller clarification uses existing resume/answer path; native question response goes to pending attempt, not a new Controller invocation.
3. Multiple pending requests: show available requests and let user select one explicitly; don't force one active model, don't infer which model needs answer, no auto-select from role. Input routing via existing C13 correlation. EOF/non-TTY: do not block on stdin; existing configured permissions honored, otherwise explicit unavailable/cancel/timeout per contract; not default approve/deny silently; headless clarification retains existing waiting/resume behavior. Ctrl-C follows existing cancel policy (current request/input vs operation explicitly distinguished by existing CLI contract; document actual behavior), no new blind cancellation of independent operations; terminal restoration on error/exit/signal.
4. Live owner/local control: CLI attached client receives scoped activity/execution notices through C13 endpoint; answer existing pending request with valid owner binding; observer cannot answer merely because it sees event. Reuse requestId/token/configurationRef/single owner; no background daemon, no new store writer. Reconnect no replay of unknown commands, explicit inspect current pending/operation; no stale answer forwarded. Preserve other run/resume/inspect/cancel/trace/export behaviors. CLI can work directly and through owner; no duplicate display if both sources present.
5. Tests using pseudo-terminal/subprocess and actual control endpoint: streaming before process exit; no subscriber non-TTY output compatibility; multiple requests, correct input, deny/timeout/EOF/Ctrl-C, disconnected client, restored terminal, slow output, final exactly once, repeated run/resume IDs, wrong owner, errors and no leaked tokens. Test no changes to execution records and counts across modes.
