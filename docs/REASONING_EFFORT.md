# Адаптивный reasoning effort

**Статус: C11R реализован и проверен на автоматизированных fixtures; поддержка конкретных внешних моделей/версий, нативные пробы CLI/ACP и Zed остаются UNVERIFIED до C12.** Это расширение существующего выбора исполнителя и единого цикла координации. Оно не вводит отдельный Router, scheduler, классификатор сложности или обязательное делегирование.

## 1. Владение и границы

Controller оценивает сложность, неопределённость, требования и пользу дальнейшей работы. Он выбирает профиль и reasoning level специалиста, собственный effort следующего хода, необходимость самостоятельного продолжения, делегирования или завершения. Модель может изменить решение после новых observations либо продолжить рассуждение на уже доступном контексте.

Host проверяет форму и идентичность решения, членство выбора в доверенном каталоге, полномочия, отмену и ресурсы. Application разрешает пользовательское соответствие level → native effort. Адаптер проверяет техническую поддержку и передаёт значение через контракт конкретного провайдера. Core не знает нативные имена, flags или ACP option ids.

Нет обязательного внешнего события между самостоятельными ходами Controller. Нет специальных квот на смену effort, запрета понижения, правила «повысить после N ошибок», оценки полезности хода Host или обязательного специалиста для более глубокого анализа. На данном этапе отдельный механизм предотвращения циклической смены effort не вводится. Возможные изменения поведения рассматриваются по реальным наблюдениям, а не предполагаемому риску.

Обычные ограничения operation, cancellation и правила неизвестных эффектов продолжают действовать для всех вызовов. Это не новые ограничения reasoning. Разрешённая самостоятельная работа не гарантирует полезность каждого хода; Host не оценивает её семантически.

## 2. Доверенная конфигурация профиля

Расширение остаётся в **config schemaVersion: 1**. Отсутствие `reasoningEffort` эквивалентно `"native"` для новых вызовов. Это сохраняет поведение существующих конфигураций; runtime schema/decoder принимают новые необязательные поля без повышения версии.

```json
{
  "profiles": {
    "primary": {
      "provider": "provider-a",
      "model": "model-a",
      "reasoningEffort": [
        { "level": "medium", "effort": "medium" },
        { "level": "xhigh", "effort": "high" }
      ],
      "defaultReasoningLevel": "medium"
    },
    "specialist": {
      "provider": "provider-b",
      "model": "model-b",
      "reasoningEffort": [
        { "level": "high", "effort": "high" },
        { "level": "xhigh", "effort": "ultra" }
      ],
      "defaultReasoningLevel": "high"
    },
    "unmanaged": {
      "provider": "provider-c",
      "model": "model-c",
      "reasoningEffort": "native"
    }
  }
}
```

Это фрагмент действующей конфигурации профилей, а не самостоятельный launch-файл. Модели, providers и нативные значения иллюстративны; поддержка проверяется для конкретного исполнителя.

- `reasoningEffort`: отсутствует, строка `"native"` либо непустой массив объектов `{level, effort}`.
- `level`: непустой унифицированный идентификатор выбора. Рекомендуемый общий словарь: `minimal`, `low`, `medium`, `high`, `xhigh`. Пользователь сам сопоставляет им значения моделей. Например, `xhigh` → `xhigh` для одной и `xhigh` → `ultra` для другой.
- Идентификаторы расширяемы через доверенную конфигурацию, а не закрытый enum в core. Пользователь должен применять одинаковые имена последовательно. Это унификация названий, не доказательство равной мощности моделей или универсальная шкала качества/стоимости. Host не сортирует уровни и не выбирает «ближайший».
- `effort`: непустая строка нативного значения, непрозрачная для core. Adapter проверяет её по своему известному контракту/доступным данным negotiation. Нативные значения не являются shell-фрагментами.
- `level` уникален внутри профиля. Порядок массива значения не имеет. Неполный набор уровней допустим; неуказанный уровень недоступен.
- Для одного элемента default можно опустить: он однозначен. Для нескольких элементов `defaultReasoningLevel` обязателен и должен ссылаться на элемент массива. Это deterministic default, не интеллектуальное решение Host.
- При `"native"` или отсутствии массива `defaultReasoningLevel` запрещён. `null`, пустой массив, неизвестные поля и другие строки вместо `"native"` дают точную ошибку JSON path.
- `"native"` означает **не переопределять настройку**. Провайдер может рассуждать и иметь собственные defaults, в том числе в нативном launch profile. Не передавать строку `native` как effort и не переименовывать её в medium.
- Mapping принадлежит доверенному user config. Project preferences, текст модели и skill не добавляют levels/native values и не меняют permissions. Новый project override для effort не требуется.

Один provider/model может иметь несколько профилей по существующим причинам. Создавать профиль на каждый effort не требуется. Эффективная настройка для конкретного вызова имеет приоритет над нативным default только при selectable-выборе; adapter обязан проверить и документировать этот приоритет. В режиме native сохраняется прежний порядок нативных настроек.

## 3. Каталог и выбор специалиста

Модельный каталог профиля содержит `reasoning: {mode: "native"}` либо `{mode: "selectable", levels: [...], defaultLevel: "..."}`. Сообщать доступные сведения о поддержке с источником и областью provider/model/session. Доверенное объявление, известная поддержка adapter и ответ конкретной сессии не равны друг другу. Не выдавать неизвестное за unsupported.

Нативный mapping и launch settings не нужны Controller; adapter получает разрешённое значение отдельно. Не передавать секреты или неограниченный provider payload в каталог.

В существующий delegate Action добавляется необязательное `reasoningLevel`:

```json
{
  "actionId": "review-concurrency",
  "kind": "delegate",
  "profileId": "specialist",
  "reasoningLevel": "xhigh",
  "objective": "Проверь корректность конкурентного восстановления",
  "contextRefs": [],
  "dependsOn": [],
  "expectedResult": "Выводы, основания и оставшиеся неопределённости"
}
```

При отсутствии поля используется default выбранного selectable-профиля либо native. Явный отсутствующий level даёт адресный отказ action до модельного prompt; независимые разрешённые actions продолжаются. Controller получает причину и актуальные доступные варианты. Отсутствующий default не разрешается случайным первым элементом.

Разные actions одной operation могут иметь разные profiles/levels. Следующее действие может изменить effort в любую сторону. Уже запущенный invocation не перенастраивается. Effort — параметр вызова, а не обязательная стадия, роль, оценка достаточности evidence или изменение прав.

## 4. Следующий ход Controller

Начальный Controller использует default своего выбранного профиля либо native. Для динамики добавляется необязательное поле Decision:

```json
{
  "nextController": {
    "reasoningLevel": "xhigh",
    "continue": true
  }
}
```

Это фрагмент Decision; остальные обязательные поля существующего контракта сохраняются.

- `reasoningLevel` выбирается из текущего разрешённого Controller-профиля. Смена самого Controller-профиля не входит в это расширение.
- `continue: true` — явное решение модели сделать следующий самостоятельный ход, в том числе на том же контексте и с тем же effort. Не требуется action, ответ пользователя или событие внешнего исполнителя.
- `continue` можно опустить, когда другое решение уже предусматривает следующий ход, например после результатов specialists. Одно изменение настройки без содержательного управляющего действия не создаёт автоматического вызова.
- `nextController` не пуст; содержит level, `continue: true` или оба. При level без continue должны оставаться действительные additions/cancellations/wait и другие предусмотренные основания следующего хода. Пустой Decision по-прежнему INVALID_PROPOSAL.
- `nextController` несовместим с finalAssessment и clarification: после завершения или ответа пользователя новый цикл начинается с действующего default. Для ожидания worker допустим level вместе с waitPolicy, но `continue: true` и waitPolicy взаимоисключающие.
- Additions и `continue: true` совместимы: допустимые workers запускаются обычным coordinator, следующий Controller получает pending/results snapshot, соблюдая общий лимит. Не добавлять новый scheduler, общее обязательное ожидание workers или второй конкурирующий Controller.
- Выбор **одноразовый**: применяется к следующему новому Controller invocation, затем используется default, если модель не предложила новый выбор. При continue без level используется default. Это не липкая глобальная настройка. Каталог/контекст показывают текущий фактический выбор, default и pending selection.
- Принятое решение и привязка его выбора к следующему attempt сохраняются долговременно. Повтор Decision, CAS retry или redelivery не потребляют выбор дважды. Первая новая попытка Controller, в том числе correction-вызов, потребляет выбор; повтор доставки результата не является новым вызовом.
- Pending selection, ещё не использованный до crash, сохраняется при техническом recovery, даже если generation счётчик увеличился. Только явное пользовательское продолжение/superseding решение снимает прежний pending выбор и использует действующий default; прошлые routes не меняются. Если dispatch уже мог состояться, нельзя считать выбор неиспользованным и автоматически повторять попытку.
- Последовательные самостоятельные ходы, включая чередование levels, разрешены до обычного общего ресурсного предела. Effort-specific anti-loop gate не вводится.

### Неподдерживаемый выбор Controller

Если Controller запросил для себя неизвестный/неподдерживаемый level, либо adapter явно не способен применить выбранное значение, **показать техническую ошибку пользователю**. То же относится к неподдерживаемому стартовому default.

Не делать автоматическую correction-сессию на прежнем effort, silent downgrade, повтор с default или принудительную делегацию. Сохранить operation, причину, профиль/level, доступные варианты и имеющийся прогресс. Использовать существующий technical waiting/result path, а не новую state machine. Для продолжения нужен явный пользовательский resume после выбора допустимой конфигурации/решения; старый расход сохраняется.

Независимые уже разрешённые worker actions не отменяются из-за ошибки настройки Controller; их результаты сохраняются. Ошибка собственного выбора адресуется next Controller dispatch, а не автоматически всей партии additions. Последующие действия без нового действительного решения не придумываются. Публичные API, CLI и ACP показывают ошибку явно, без пустого успешного ответа и ложного complete.

Не путать неподдерживаемую настройку с отсутствием acknowledgment. Последнее не является этой ошибкой.

## 5. Разрешение, dispatch и provenance

Владение распределено однозначно:

| Этап | Владелец | Сохраняемый смысл |
|---|---|---|
| Mapping | Доверенная конфигурация | Разрешённые level → native effort |
| Выбор | Controller или deterministic default | Запрошенный level и источник выбора |
| Материализация | Application/catalog resolver | Разрешённое native value и configurationRef |
| Передача | Provider adapter | Что и каким поддерживаемым интерфейсом было передано |
| Acknowledgment | Provider через adapter | Что подтвердил/отклонил источник, если сообщает |
| Применимость результата | Модель | Достаточность сведений для задачи |

Расширить существующие Profile/Catalog, Action, Decision, Invocation и Attempt.route. Отдельная сущность исполнения или вторая история reasoning не нужна.

Invocation передаёт неизменяемый разрешённый выбор. Для новой route использовать `reasoning: {mode: "native"}` либо `{mode: "selectable", level, nativeValue, selectionSource}`, где selectionSource различает `model` и `default`. Для воспроизводимости остаются configurationRef, profileId, providerId, model и idempotencyKey. Логический запрос сохраняется в Decision/Action; конкретная route фиксирует разрешённое назначение попытки. Нативное значение не восстанавливается задним числом из нового конфига.

Route — намерение dispatch, не доказательство отправки настройки или её исполнения. Факты adapter submission/acknowledgment хранятся как коррелированные observations с attemptId, источником и временем; route не переписывается. Отсутствие observation означает отсутствие сведений, а не отказ.

Различать `configured` (разрешено конфигом), `submitted` (адаптер передал значение) и `acknowledged` (провайдер подтвердил настройку). Это минимальный словарь фактов, не обязательная цепочка gates. Даже acknowledgment не измеряет внутренний объём reasoning и не доказывает качество ответа. Host-observed передача и provider-reported подтверждение имеют разное provenance.

Старые snapshots без reasoning читаются как **настройка исторического вызова не записана**. Это не то же, что default native для отсутствующего поля в новом конфиге. Не отбрасывать прошлые observations/findings и не выводить effort по названию модели.

Повтор с прежним idempotencyKey требует эквивалентности эффективного provider request по контракту адаптера, включая model/effort и прочие значимые параметры. Для новых worker попыток Host сохраняет в route requestHash материализованного входа (включая objective, expectedResult, инструкции/skills, выбранный контекст и constraints). При несовпадающем requestHash, неизвестном историческом hash или изменённой route повтор по provider_idempotency запрещён; альтернативные user_approval/no_effect основания не меняются. Совпадения level недостаточно после изменения mapping. Если исторические параметры неизвестны, нельзя заявить доказанную эквивалентность. Новый effort не разрешает replay неизвестного эффекта. Независимое новое рассуждение остаётся допустимым.

## 6. Адаптеры и ошибки

| Ситуация | Требуемое поведение |
|---|---|
| Значение не разрешено профилем | Адресный отказ до prompt; worker → Controller, собственный Controller → пользователь |
| Поддержанный способ передачи, отдельного acknowledgment нет | Вызов разрешён; submission recorded, acknowledgment неизвестен |
| Провайдер явно отклонил настройку до prompt | Не отправлять prompt с подменённым значением; адресная ошибка |
| Провайдер подтвердил значение | Сохранить provider-reported факт без вывода о качестве |
| Расхождение/отказ обнаружен после возможного prompt dispatch | Сохранить результаты и реальные сведения об эффекте; сообщить расхождение, не повторять автоматически |
| Невозможно получить диагностические metadata | Не блокировать вызов только из-за отсутствия metadata |

Отсутствие достоверного механизма передачи выбранной настройки — capability error. Отсутствие отдельного подтверждения после передачи по поддержанному контракту — информационная неопределённость. Не объединять их в один `confirmed` gate. Не путать uncertainty effort с неизвестностью внешних эффектов.

**CLI:** проверить официальный контракт установленной версии и приоритет над native profile; передавать параметр отдельными argv без shell interpolation. Native mode не добавляет override. Adapter не реконструирует effort из текста задачи. Флаги/ключи зафиксировать только после проверки, включая ошибки и cancellation.

**Generic ACP:** использовать возможности конкретного агента/model/session. Сначала выбрать модель, затем получить актуальные config options, выбрать однозначно определённый selector, проверить значение и выполнить поддерживаемый запрос до prompt. Selector задаётся документированным protocol contract либо явной доверенной adapter-конфигурацией. Не угадывать его regex/названием/первой похожей опцией; не предполагать обязательность категории reasoning для любого ACP агента. При смене модели options могут измениться. Отсутствие достаточного acknowledgment само по себе не добавляет gate. Параллельные attempts не должны менять effort друг другу; настройки принадлежат соответствующей сессии.

**Plugins:** тот же общий Invocation/ProviderPort. Адаптер может реализовать другое нативное представление без provider branching в core. Native-профили старых расширений продолжают работать. Если расширение не умеет selectable-setting, явно отказать именно в выбранной возможности; не молча игнорировать поле.

## 7. Диагностика и качество

Inspect/trace/export показывают profile/model, logical level, источник default/model, mapping/configurationRef и доступные submission/acknowledgment facts с их авторством. Для Controller дополнительно доступны причина следующего хода (decisionId), pending/consumed selection и адресная ошибка. Старые маршруты объяснимы без текущего plugin или исходного config. Соблюдать существующие redaction, bounded output и правила capture; hidden chain of thought не требуется.

Все вызовы, включая самостоятельные Controller и неудачные, учитываются существующим ledger. Native usage остаётся measured либо unknown; не изобретать цену уровней. Разные уровни не меняют authority, concurrency, ownership, cancellation или правила recovery.

Тесты с управляемыми решениями доказывают корректность координации, а не оптимальность выбора LLM. Реальные пробы должны отдельно установить поддержку конкретных providers/versions и наблюдаемую полезность: качество результата, время, доступный usage и ненужные делегирования. Эффективность — проверяемая цель, не обещание автоматического улучшения от высокого effort.

## 8. Фактически реализованные границы и проверка

- Schema v1: `reasoningEffort` и `defaultReasoningLevel` принимаются trusted decoder, не project preferences. Модель видит только `mode`, логические уровни, default и источник; **не** значения нативного mapping. Отсутствие поля в старом snapshot/route означает `not_recorded`, а не выбранный сейчас default.
- `Action.reasoningLevel` проверяется при admission конкретного worker. `Decision.nextController` с `continue:true` даёт самостоятельный новый Controller turn без новых событий/делегирования; выбор привязывается через `reasoningDecisionId` к одной попытке и фиксируется в `Attempt.route.reasoning`. При явном пользовательском продолжении pending выбор сбрасывается; технический recovery не потребляет его.
- ProviderPort с `supportsReasoningSelection: true` подтверждает, что адаптер **умеет принимать** selectable-выбор. Старые плагины без флага выполняют native; selectable отклоняется до `open()`. Это декларация поддержанного пути, не гарантия нативного ACK.
- Codex CLI: для selectable-профиля в argv конкретной попытки добавляется `-c model_reasoning_effort=<nativeValue as JSON string>`; `native` не добавляет override и сохраняет профиль через `--profile`. Значение не формируется из model prompt и не исполняется shell. Версия реального Codex и его подтверждённое поведение должны проверяться отдельно.
- Generic ACP: после выбора модели адаптер использует единственный `select`-selector категории `thought_level` из `session.configOptions`, проверяет допустимость нативного значения, вызывает `session/set_config_option`, проверяет effective value и неизменность model перед `session/prompt`. Агенты, не публикующие такой selector, пока **не поддерживают selectable** в этом адаптере. Протокольные fixtures не доказывают совместимость всех ACP агентов.
- `operationTrace` показывает requested/source/effective выбор, configurationRef, dispatchCertainty и записанное ACP config-option acknowledgment (если доступно). Его отсутствие равно `not_recorded`, **не** failure. Отдельное подтверждение настройки не измеряет внутренний ход рассуждения. Trace/export ограничены размером, используют redaction, но оператор не должен включать в них secrets без доверенной конфигурации redaction.
- Неподдерживаемый собственный Controller level приводит к явному `CAPABILITY_UNAVAILABLE` с operation/profile/known levels, без fallback. Для продолжения нужен пользовательский follow-up/resume с действующим trusted config. Ни один уровень не получает специальную квоту или ранжирование интеллекта.

Подробные протоколы автоматизированных тестов и реальных native-проб — служебные материалы разработки и не входят в пакет продукта. Следующий C12 повторно проверяет интегрированный продукт целиком.
