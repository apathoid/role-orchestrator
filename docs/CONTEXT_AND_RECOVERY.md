# Контекст, findings и восстановление

## Модель знания

Хранить отдельно: сообщение пользователя; сообщение модели; событие инструмента; наблюдение transport/Host; finding модели; итоговую assessment; пользовательское принятие. `provider_reported` не равно `host_observed`. Поле `exitCode` относится только к тому процессу, чей exit действительно доступен.

ProviderPort передаёт тип события, идентификатор источника, доступный вывод и его полноту. Доверенный адаптер сообщает наблюдавшийся выход процесса агента как `agent_exit`, а отдельно полученный результат инструмента как `provider_tool` с необязательным кодом завершения инструмента. Текст модели сохраняется с `model_claim`, общий отчёт провайдера с `provider_reported`. Число внутри произвольного payload и метка exit в ссылке на результат сами по себе не образуют наблюдение выхода процесса или инструмента.

Координатор отмечает время приёма по своим часам. В контексте порядковый номер задаётся парой из revision события и позиции наблюдения в этом событии. Порядок фиксирует запись в истории, а время отражает получение от источника, в том числе при параллельных попытках. При повторном открытии сохраняются эта корреляция, доступный вывод и исходная полнота. Для снимков v1, записанных до появления provenance, сохраняются имевшиеся данные без реконструкции отсутствующих деталей.

При приёме наблюдения `observe` возвращает внутреннюю ссылку, однозначную в пределах операции. Исходная ссылка остаётся в `providerRef` и служит коротким именем только для результата той же попытки. Два вызова с одинаковым именем провайдера получают разные ключи. Повтор идентичной записи в одном вызове сохраняет прежний ключ, противоречащее повторное сообщение отклоняется. Для межвызовных ссылок используются внутренние ключи. Если короткое имя совпадает с исторической ссылкой, требуется явный внутренний ключ. Неоднозначный сохранённый снимок отклоняется локальным store при декодировании.

Наблюдения неизменяемы по смыслу. Исправление ошибочной атрибуции создаёт связанную запись, не стирает исходную. Finding может иметь несколько модельных оценок, `supersedes` и опоры; объединение делает модель. Host не объединяет находки по совпадению текста/пути и не присваивает severity автоматически.

Controller передаёт структурированные находки в необязательном `Decision.findings`. Для специалиста адаптер может передать тот же список в `ProviderResult.findings` отдельно от обычного вывода. `author` совпадает с ID профиля, выполнившего вызов. Находка доступна в контексте под ссылкой `finding:<findingId>` с атрибуцией `model_claim`. В `supports` можно ссылаться на наблюдения и ранее объявленные находки той же операции. `supersedes` ссылается на предыдущую структурированную находку и сохраняет обе записи вместе с их опорами. Итоговая assessment может сослаться и на находки из того же Decision.

## Доставка контекста

Контекст ограничивается реальным размером окна и конфигурацией. Обязательный минимум для каждого handoff: цель, ограничения, активные неизвестные эффекты, относящиеся к подзадаче результаты и явный список недоступных частей. Недавние события/незакрытые requirements имеют структурный приоритет; семантический выбор релевантных findings принадлежит Controller.

В C06.3 доверенная настройка `context.maxBytes` задаёт предел UTF-8 JSON для необязательных записей истории на один вызов (по умолчанию 65 536 байт). Controller получает недавние записи с приоритетом по порядку журнала, а специалист получает историю по `Action.contextRefs` в порядке выбора Controller. Технический контекст формируется для конкретного получателя перед dispatch. Цель, буквальный пользовательский ввод и ограничения, конфигурация вызова и технические сведения об отмене и неизвестных эффектах передаются сверх лимита истории. Полный лимит окна зависит также от формата и возможностей адаптера.

Большая запись передаётся с `completeness: truncated`, `excerpt` и исходным `ref`. Для структурированного значения excerpt содержит начало JSON, помеченное как частичный текст. Метаданные provenance и исходная запись остаются доступны. Для выбранных ссылок `unavailableReason` различает `missing` (ссылка неизвестна), `payload` (известна только ссылка на вывод) и `budget` (запись пропущена из-за лимита). При сокращении общей истории Controller получает число пропущенных записей и фрагментов. Содержимое журнала при формировании контекста сохраняется целиком.

Raw артефакты хранятся по ссылке с размером, hash для проверки байтов и признаком truncation. Hash не доказывает истинность содержимого или актуальность исходников. Модель может запросить деталь через разрешённый context fetch; вторая модель не получает все секреты первой только из-за общей operation.

При нехватке окна сначала ограничить вывод и предоставить ссылки, затем при необходимости запросить модельное резюме. Summary имеет автора и диапазон covered observations, не заменяет raw records. Обрезание не должно молча убирать user restrictions, cancellation или unknown effects. Не создавать отдельный retrieval/vector сервис до доказанной потребности.

`Invocation.contextAccess.list(cursor?)` перечисляет метаданные истории от новых записей к старым. Страница ограничена 32 записями и 8 КиБ JSON, включая курсор. Controller может обнаружить пропущенные записи своей операции, а специалист видит только выбранные для него ссылки. Перечисление и fetch истории необязательны: модель самостоятельно определяет необходимость дополнительного retrieval, если уже доставленного контекста достаточно. Для слишком длинной исторической ссылки каталог возвращает позицию в журнале, которую принимает fetch в том же вызове. Разрешение на чтение конкретной записи другой операции действует через fetch.

`Invocation.contextAccess.fetch(ref, sourceOperationId?)` возвращает ограниченную запись истории или байты сохранённого артефакта. Controller видит историю своей операции на момент dispatch. Специалист запрашивает только ссылки из handoff. Для другой операции требуется доверенное решение `allowContextShare` для пары операций, ссылки и профиля. Отмена, завершение вызова и отзыв полномочий закрывают доступ. Причины недоступности различают неизвестную ссылку, отсутствие байтов, предел размера, отказ в доступе и нарушение целостности.

Доверенный адаптер может сохранить доступные байты через `captureArtifact(bytes)`. Он дожидается результата перед завершением вызова и передаёт модели выданную ссылку. Запись операции привязывает эту ссылку к опубликованному артефакту. Строка с хешем или JSON-отчёт модели остаётся данными. При чтении локальный store проверяет размер и хеш, а запись и выдача байтов ограничены `context.maxBytes`. Для inline-записи fetch может вернуть более длинный явно помеченный фрагмент в пределах этого лимита.

Адаптер передаёт подготовленное моделью резюме как наблюдение `model_summary` с текстом и `coveredObservationRefs`. Координатор сохраняет его с авторством вызванного профиля и источником `model_claim`, проверяя ссылки на уже доступные исходные наблюдения этой операции. Сохранённое резюме можно получить отдельно от исходных записей.

## Чего не делать

Нет глобальных `fresh/stale` для всех findings, evidence quorum, подтверждения «достаточно доказательств» Host, обязательного historical/current reconciliation, source epoch для допуска работы или привязки Store revision к checkout. Модель может пометить конкретный finding нерелевантным, оставить его открытым или проверить заново.

## Локальная долговременность

State directory задаётся доверенной конфигурацией вне исходников проекта по умолчанию. Каталог должен поддерживать выбранные атомарные файловые операции; неподходящая FS — явная ошибка именно storage. Первый вариант: один JSON snapshot на operation, temp write -> flush -> atomic rename, с доступной платформенной directory sync и явным описанием границы crash guarantees. Артефакты — отдельные ограниченные файлы с атомарной публикацией до ссылки из snapshot. Не вводить параллельно event-sourcing log как вторую истину.

Эксклюзивность writer относится только к собственному state directory. Предпочесть проверенную библиотеку локальной блокировки, выбранную при реализации; не писать универсальную distributed lease. После аварии lock recovery должен различать живого владельца и мёртвый процесс, не снимать lock лишь по возрасту; при невозможности доказать владение дать адресную диагностику/ручное освобождение. Это ограничение storage, не workspace freshness.

Snapshot revision монотонна. commit с прежней revision возвращает conflict; приложение перечитывает запись. Несовместимая версия не перезаписывается. Поддержка будущего обновления формата нужна, импорт неизвестной старой системы не нужен. Повреждение одной operation не должно делать недоступными все остальные.

## Матрица сбоев

| Место сбоя | Сохранённое знание | Действие |
|---|---|---|
| До reservation и до dispatch | Вызов не отправлен | Обычное новое предложение разрешено |
| Есть только reservation, процесс умер | Dispatch ещё не разрешён | Сохранить not_sent и расход, продолжать по новому решению модели |
| Dispatch записан, процесс умер до исхода | Отправка могла произойти | Восстановить unknown, не переисполнить скрыто |
| Provider достоверно отказал до отправки | Эффекта данного вызова не было | Controller может изменить профиль/вход; общий бюджет сохранён |
| Provider потерян после dispatch | Возможные эффекты, часть контекста | Status lookup при наличии; иначе модельное продолжение с uncertainty |
| Outcome получен, commit неизвестен | Возможно уже сохранён | Load по attemptId, повтор только внутренней записи |
| Outcome сохранён, клиент не получил ответ | Факт сохранён | Повторная доставка ответа без повторного инструмента |
| Cancel отправлен, ACK нет | Нет гарантии прекращения | Late events допустимы; новые dispatch отменённого действия запрещены |
| Диагностический файл заполнен | Бизнес-state может быть исправен | Drop/rotate диагностики; отдельное предупреждение без ложной task failure |
| Изменились файлы или Git | Только обычная среда | Нет обязательного host recovery |

## Неизвестный эффект

Не создавать Host-анализатор семантической эквивалентности произвольных команд. Техническое правило узкое: автоматически не воспроизводить прежний attempt после неопределённого dispatch. Если модель предлагает повторить операцию с возможным необратимым эффектом, она должна учитывать предыдущий исход; повтор безопасен при известной идемпотентности/доказанном отсутствии эффекта либо информированном разрешении пользователя на риск. Провайдерская idempotency key используется только если контракт действительно её поддерживает.

Независимое чтение, уточнение, анализ и другой разрешённый путь не блокируются существованием unknown. Unknown не превращается в глобальное состояние «всё запрещено». Отсутствие изменений в файлах не доказывает отсутствие внешнего эффекта. Текст модели «вероятно ничего не произошло» не является наблюдением транспорта.

## Retention

`inspectFinding(operationId, ref)` показывает находку и цепочку её опор в пределах операции. Для записи с попыткой доступны outcome исходной записи и текущее состояние попытки. Инспекция показывает наличие артефакта без чтения тела, а context fetch проверяет размер и хеш при выдаче байтов.

Доверенная настройка `storage.artifactRetention` передаётся при открытии локального store. `maxAgeMs` отсчитывается от последнего записанного события операции, `maxBytes` применяется к суммарному объёму артефактов, которые можно удалить, начиная с наиболее старых. Для общего blob учитывается наиболее поздняя операция. Политика применяется при открытии под блокировкой writer. Активные операции, операции в ожидании и попытки с возможным или неизвестным эффектом защищают свои артефакты, включая общие blob. Если какой-либо снимок нельзя прочитать однозначно, проход очистки пропускается.

Снимок, находка, итог и ссылки сохраняются. При удалении опубликованного blob локальный store сохраняет маркер причины, и context fetch возвращает `unavailable` с причиной `retention`. Присутствующий blob остаётся читаемым после неудачного unlink. Повторная публикация тех же байтов восстанавливает доступ по прежним ссылкам. Экспорт диагностики по запросу редактирует секреты и не меняет рабочее состояние.

Snapshot v1 хранит целостную operation: идентичность и revision, ссылки на доверенную конфигурацию и сообщения, историю решений и допущенных действий, attempts и их ledger. Источник учёта — записи attempts. Неизвестный usage записывается как JSON null, а известный ноль — как число. Необязательные поля можно опустить. Неизвестная версия отличается от повреждённого snapshot.

Состояние хранит ссылки, а не объекты адаптера, AbortSignal, живые permission tokens или секреты конфигурации. Значения observations ограничены JSON-данными. Их поставщик отвечает за исключение секретов из полезной нагрузки.

Локальный store открывает заранее созданный каталог на локальной файловой системе с поддержкой атомарного rename, file/directory sync и межпроцессных блокировок SQLite. JSON-файл публикуется через временный файл в том же каталоге. Ошибка после rename может означать, что новая полная версия уже видна, поэтому вызывающий перечитывает snapshot. Повторное подтверждение той же revision возможно только при точном совпадении записи с сохранённой. При этом store снова синхронизирует каталог без перезаписи snapshot. В списке нет временных файлов и служебных файлов lock. Несовместимый или повреждённый snapshot не перезаписывается.

Исключительность writer реализует транзакция `BEGIN IMMEDIATE` через встроенный `node:sqlite`. SQLite-файл служит для блокировки каталога, а operation хранится в JSON. При закрытии соединения или гибели процесса блокировка освобождается. Сам lock-файл остаётся на месте, его возраст не влияет на допуск. Файловые гарантии проверены на Linux. Сетевые и иные файловые системы без этих свойств не входят в проверенную конфигурацию.

При явном resume незавершённой operation coordinator восстанавливает историю и ledger, применяет текущий доверенный grant и лимиты и запускает новый ход Controller. Завершённая operation может вернуть сохранённый ответ. Уточнение требует связанного пользовательского ответа. После restart прежние attempts без живого владельца освобождают слот, а их расход и возможные внешние эффекты сохраняются.

Опциональный `lookupStatus` относится к исходному attempt. Вызов допустим при совпадении сохранённого маршрута и доверенной конфигурации, действующем grant и negotiated capability `attempt.status`. Результат имеет provider provenance. Позднее подтверждение уточняет исход попытки, а решения предыдущего Controller из этого ответа не исполняются. Недоступная проверка статуса оставляет неопределённость видимой для модели.

Явный повтор задаётся новой action с `retryOf` и `retryBasis`. Coordinator допускает `no_effect` для известного исхода без эффекта, `user_approval` при текущем доверенном решении для этой пары attempt/action и выбранного профиля либо `provider_idempotency` с прежним ключом на том же подтверждённом маршруте. Ключ хранится только для адаптеров, заявивших `supportsIdempotency` как свой контракт. Такой адаптер отвечает за дедупликацию эффекта по ключу и отказ при изменившемся логическом запросе с тем же ключом. Конфигурация и текст модели сами по себе этих полномочий не дают. Неопределённый исход остаётся в истории и не мешает независимым действиям.

List возвращает исправные snapshots и отдельные записи `unavailable` с непрозрачной ссылкой и причиной. Имена новых snapshot-файлов содержат digest operationId и начального requestId. Поэтому повреждённое тело не позволяет повторной доставке того же начального requestId запустить новый вызов. Снимки раннего формата с digest только operationId остаются читаемыми и обновляемыми. Если такой снимок повреждён и его requestId неизвестен, новые submit отклоняются до восстановления записи, а доступные существующие операции по-прежнему можно читать и продолжать по operationId.

При чтении snapshot coordinator проверяет представление attempt ledger по упорядоченным событиям reservation, dispatch и outcome. Противоречие в собственном состоянии возвращается как corrupt_snapshot. В частности, запись о dispatch не может стать доказательством отсутствия отправки из-за изменённого статуса attempt.

## Граница применимости проверок

Результаты проверки сохраняются как исторические observations с происхождением; mutable workspace или изменение ветки не требует остановки либо перепроверки со стороны Host. Актуальность выводов — решение модели. После crash запись `unknown` означает неопределённость внешнего эффекта: не заменять её `none` из противоречивого snapshot и не выполнять blind replay. Тесты с поддельным исполнителем фиксируют этот контракт, но не доказывают его соблюдение любым нативным CLI/ACP агентом.

### Восстановление принятых Actions

Journal admissions, cancellation, reservations и outcomes определяют восстановление. Принятый, ещё не отправленный Worker может продолжиться после restart, включая локальную техническую остановку Controller; reserved/not_sent сохраняет attempt id и charge. Dispatched orphan остаётся unknown/lookup, terminal не воспроизводится. Не запускаются отменённые/отклонённые actions или действия без выполненной model-acceptance зависимости. Локальный Controller failure сохраняется; recovery не вызывает автоматический повтор Controller. Для явного продолжения Controller используется существующий user follow-up.

C12R.4: ContextPort directory metadata includes the technical unavailable reason when known. A known reference whose payload has disappeared is distinct from an oversized but present artifact; retention, missing payload, ambiguity and budget remain distinct. A legacy ambiguous reference exposes neither competing record, including positional fetch. This does not introduce a semantic retrieval or freshness gate.


## C12R.9 — непрерывность без нового хранилища

Исходная история остаётся неизменным Operation journal с observations, outputRefs, attribution, attempts, Decisions и artifact receipts; ContextPort.list/fetch продолжает читать её через действующие operation scope, authority и retention. Host формирует из этих записей ограниченную доступным контекстом техническую карту `host:invocation-context.value.workMap`: `total/represented/omitted`, исходные `actionId/attemptId`, указатель `objectiveRef` на Decision, lifecycle, dispatchCertainty, terminal/effect, outputRefs/observationRefs и capture completeness. Map не является индексом, persisted state, семантическим резюме или обещанием наличия raw bytes. Не отображённые в карте результаты остаются в исходной истории и в страницах ContextPort; завершённые попытки с `effect=unknown/possible` отдельно отмечаются в `effectUncertainties` и не трактуются как незавершённые.

Controller может *сам* запросить историю в принятом `Decision.nextController:{continue:true,contextRequest:{refs:[...],cursor?:n}}`, без обязательного MCP и без нового Worker. Единственный следующий Controller invocation использует обычный разрешённый ContextPort, чтобы доставить явно выбранные refs или страницу каталога `host:history-page:n`, с явной полнотой и причинами отсутствия; без запроса прежний путь не меняется. Внешние MCP context_list/fetch остаются опциональны. Выбор нужных refs, новых проверок и момента остановки принадлежит модели. Нет Host summarization/compaction, semantic score, принудительного replay или сохранения одной native session.

История, полученная явно по запросу, резервирует фактически занимаемое место в Controller byte budget перед необязательной технической картой. Исходные observations/provenance и ссылки не переписываются при удалении технически доказанных inline-дубликатов отображения. Literal user input остаётся обязательным, даже если превышает optional budget; при недостаточном лимите неполнота не скрывается.


### C12R.9 review — исходные результаты, достоверность и поток данных

Для финального сообщения Worker adapter (Codex CLI или ACP) может указать `ProviderResult.outputObservationRef`, если то же завершённое сообщение уже отправлено как observation данного invocation. Coordinator проверяет указанную внутреннюю ссылку, наличие её в `Outcome.outputRefs`, source/provenance, completeness и точное совпадение UTF‑8 байтов с финальным `result.output`. Только в таком случае не создаётся дополнительный `attempt-output`; оригинальные observation/outcome/ref остаются в Operation. Совпадение произвольных текстов разных sources/attempts не используется как доказательство идентичности. При отсутствии доказательства прежний `attempt-output` сохраняется.

`host:invocation-context.value.technicalCoverage` всегда содержит точные `total/represented/omitted` для `actions`, `unresolvedAttempts`, `effectUncertainties`, `cancellations`, `outcomes`, `pendingAttempts`. Нулевая длина preview при положительном `total` означает неполную доставку, не отсутствие факта. `workMap` имеет read-only `cursor/nextCursor/represented/omitted`. При необходимости Controller выбирает `nextController.contextRequest.workCursor` для другой страницы той же производной карты. Бюджет по умолчанию остаётся **256 КиБ**; режим 512 КиБ — только конфигурация для сравнительного эксперимента.

Для записи, сохранённой полностью, но превышающей лимит одной выдачи, доступен *необязательный* `ContextPort.fetch(ref, sourceOperationId?, {offset})`. Offset отсчитывается в байтах исходного UTF‑8 (или канонической JSON-представленной сохранённой value, или фактически сохранённых байтах artifact). Ответ `kind:chunk` содержит `base64`, `offset`, `totalBytes`, необязательный `nextOffset`, `format` и метаданные provenance/receipt. Нативный `context_fetch` через MCP принимает тот же `offset`; Controller без MCP может запросить `contextRequest.refs:[{ref,offset}]` в одном из следующих *обычных* вызовов. Исходные `ContextPort.list/fetch` без offset остаются совместимы. Позиционные refs `{revision,index}` действуют и в `contextRequest.refs`; не создаётся альтернативная идентичность операции. Комбинация фрагментов восстанавливает только **фактически сохранённые** байты. `artifact.truncated=true`, source completeness=truncated, retention и integrity errors остаются видимыми: несуществующий изначальный хвост восстановить нельзя.
