# Контекст, findings и восстановление

## Модель знания

Хранить отдельно: сообщение пользователя; сообщение модели; событие инструмента; наблюдение transport/Host; finding модели; итоговую assessment; пользовательское принятие. `provider_reported` не равно `host_observed`. Поле `exitCode` относится только к тому процессу, чей exit действительно доступен.

ProviderPort передаёт тип события, идентификатор источника, доступный вывод и его полноту. Доверенный адаптер сообщает наблюдавшийся выход процесса агента как `agent_exit`, а отдельно полученный результат инструмента как `provider_tool` с необязательным кодом завершения инструмента. Текст модели сохраняется с `model_claim`, общий отчёт провайдера с `provider_reported`. Число внутри произвольного payload и метка exit в ссылке на результат сами по себе не образуют наблюдение выхода процесса или инструмента.

Новая ссылка `Outcome.outputRefs`, совпавшая с уже атрибутированным observation текущего Attempt, сохраняет `host_observed` при доверенном `host_transport`. Это независимо от exit kind: неподтверждённый exit по-прежнему понижается до `observation`; метка `ref.source` сама по себе не даёт Host provenance. Исторические ссылки не переписываются при поздней доставке тела.

Координатор отмечает время приёма по своим часам. В контексте порядковый номер задаётся парой из revision события и позиции наблюдения в этом событии. Порядок фиксирует запись в истории, а время отражает получение от источника, в том числе при параллельных попытках. При повторном открытии сохраняются эта корреляция, доступный вывод и исходная полнота. Для снимков v1, записанных до появления provenance, сохраняются имевшиеся данные без реконструкции отсутствующих деталей.

При приёме наблюдения `observe` возвращает внутреннюю ссылку, однозначную в пределах операции. Исходная ссылка остаётся в `providerRef` и служит коротким именем только для результата той же попытки. Два вызова с одинаковым именем провайдера получают разные ключи. Повтор идентичной записи в одном вызове сохраняет прежний ключ, противоречащее повторное сообщение отклоняется. Для межвызовных ссылок используются внутренние ключи. Если короткое имя совпадает с исторической ссылкой, требуется явный внутренний ключ. Неоднозначный сохранённый снимок отклоняется локальным store при декодировании.

Наблюдения неизменяемы по смыслу. Исправление ошибочной атрибуции создаёт связанную запись, не стирает исходную. Finding может иметь несколько модельных оценок, `supersedes` и опоры; объединение делает модель. Host не объединяет находки по совпадению текста/пути и не присваивает severity автоматически.

Controller передаёт структурированные находки в необязательном `Decision.findings`. Для специалиста адаптер может передать тот же список в `ProviderResult.findings` отдельно от обычного вывода. `author` совпадает с ID профиля, выполнившего вызов. Находка доступна в контексте под ссылкой `finding:<findingId>` с атрибуцией `model_claim`. В `supports` можно ссылаться на наблюдения и ранее объявленные находки той же операции. `supersedes` ссылается на предыдущую структурированную находку и сохраняет обе записи вместе с их опорами. Итоговая assessment может сослаться и на находки из того же Decision.

## Доставка контекста

Контекст ограничивается реальным размером окна и конфигурацией. Обязательный минимум для каждого handoff: цель, ограничения, активные неизвестные эффекты, относящиеся к подзадаче результаты и явный список недоступных частей. Недавние события/незакрытые requirements имеют структурный приоритет; семантический выбор релевантных findings принадлежит Controller.

В C06.3 доверенная настройка `context.maxBytes` задаёт предел UTF-8 JSON для необязательных записей истории на один вызов (по умолчанию 65 536 байт). Controller получает недавние записи с приоритетом по порядку журнала, а специалист получает историю по `Action.contextRefs` в порядке выбора Controller. Технический контекст формируется для конкретного получателя перед dispatch. Цель, буквальный пользовательский ввод и ограничения, конфигурация вызова и технические сведения об отмене и неизвестных эффектах передаются сверх лимита истории. Полный лимит окна зависит также от формата и возможностей адаптера.

Большая запись передаётся с `completeness: truncated`, `excerpt` и исходным `ref`. Для структурированного значения excerpt содержит начало JSON, помеченное как частичный текст. Метаданные provenance и исходная запись остаются доступны. Для выбранных ссылок `unavailableReason` различает `missing` (ссылка неизвестна), `payload` (известна только ссылка на вывод) и `budget` (запись пропущена из-за лимита). При сокращении общей истории Controller получает число пропущенных записей и фрагментов. Содержимое журнала при формировании контекста сохраняется целиком.

Raw артефакты хранятся по ссылке с размером, hash для проверки байтов и признаком truncation. Hash не доказывает истинность содержимого или актуальность исходников. Модель может запросить деталь через разрешённый context fetch; вторая модель не получает все секреты первой только из-за общей operation.

При нехватке окна сначала ограничить вывод и предоставить ссылки, затем при необходимости запросить модельное резюме. Summary имеет автора и диапазон covered observations, не заменяет raw records. Обрезание не должно молча убирать user restrictions, cancellation или unknown effects. Не создавать отдельный retrieval/vector сервис до доказанной потребности.

`Invocation.contextAccess.list(cursor?)` перечисляет метаданные истории от новых записей к старым. Страница ограничена 32 записями и 8 КиБ JSON, включая курсор. Controller может обнаружить пропущенные записи своей операции, а специалист видит только выбранные для него ссылки. Перечисление и fetch истории необязательны: модель самостоятельно определяет необходимость дополнительного retrieval, если уже доставленного контекста достаточно. Для слишком длинной исторической ссылки каталог возвращает позицию в журнале, которую принимает fetch в том же или последующем вызове в пределах той же операции и действующей видимости. Разрешение на чтение конкретной записи другой операции действует через fetch.

`Invocation.contextAccess.fetch(ref, sourceOperationId?)` возвращает ограниченную запись истории или байты сохранённого артефакта. Controller видит историю своей операции на момент dispatch. Специалист запрашивает только ссылки из handoff. Для другой операции требуется доверенное решение `allowContextShare` для пары операций, ссылки и профиля. Отмена, завершение вызова и отзыв полномочий закрывают доступ. Причины недоступности различают неизвестную ссылку, отсутствие байтов, предел размера, отказ в доступе и нарушение целостности.

Доверенный адаптер может сохранить доступные байты через `captureArtifact(bytes)`. Он дожидается результата перед завершением вызова и передаёт модели выданную ссылку. Запись операции привязывает эту ссылку к опубликованному артефакту. Строка с хешем или JSON-отчёт модели остаётся данными. При чтении локальный store проверяет размер и хеш, а запись и выдача байтов ограничены `context.maxBytes`. Для inline-записи fetch может вернуть более длинный явно помеченный фрагмент в пределах этого лимита.

Адаптер передаёт подготовленное моделью резюме как наблюдение `model_summary` с текстом и `coveredObservationRefs`. Координатор сохраняет его с авторством вызванного профиля и источником `model_claim`, проверяя ссылки на уже доступные исходные наблюдения этой операции. Сохранённое резюме можно получить отдельно от исходных записей.

## Чего не делать

Нет глобальных `fresh/stale` для всех findings, evidence quorum, подтверждения «достаточно доказательств» Host, обязательного historical/current reconciliation, source epoch для допуска работы или привязки Store revision к checkout. Модель может пометить конкретный finding нерелевантным, оставить его открытым или проверить заново.

## Локальная долговременность

State directory задаётся доверенной конфигурацией вне исходников проекта по умолчанию. Каталог должен поддерживать выбранные атомарные файловые операции; неподходящая FS — явная ошибка именно storage. Первый вариант: один JSON snapshot на operation, temp write -> flush -> atomic rename, с доступной платформенной directory sync и явным описанием границы crash guarantees. Артефакты — отдельные ограниченные файлы с атомарной публикацией до ссылки из snapshot. Не вводить параллельно event-sourcing log как вторую истину.

Эксклюзивность writer относится только к собственному state directory. Предпочесть проверенную библиотеку локальной блокировки, выбранную при реализации; не писать универсальную distributed lease. После аварии lock recovery должен различать живого владельца и мёртвый процесс, не снимать lock лишь по возрасту; при невозможности доказать владение дать адресную диагностику/ручное освобождение. Это ограничение storage, не workspace freshness.

Snapshot revision монотонна. commit с прежней revision возвращает conflict; приложение перечитывает запись. Несовместимая версия не перезаписывается. Поддержка будущего обновления формата нужна, импорт неизвестной старой системы не нужен. Повреждение одной operation не должно делать недоступными все остальные.

## Матрица сбоев

| Место сбоя | Сохранённое знание | Действие |
|---|---|---|
| До reservation и до dispatch | Вызов не отправлен | Обычное новое предложение разрешено |
| Есть только reservation, процесс умер | Dispatch ещё не разрешён | Сохранить not_sent и расход, продолжать по новому решению модели |
| Dispatch записан, процесс умер до исхода | Отправка могла произойти | Восстановить unknown, не переисполнить скрыто |
| Provider достоверно отказал до отправки | Эффекта данного вызова не было | Controller может изменить профиль/вход; общий бюджет сохранён |
| Provider потерян после dispatch | Возможные эффекты, часть контекста | Status lookup при наличии; иначе модельное продолжение с uncertainty |
| Outcome получен, commit неизвестен | Возможно уже сохранён | Load по attemptId, повтор только внутренней записи |
| Outcome сохранён, клиент не получил ответ | Факт сохранён | Повторная доставка ответа без повторного инструмента |
| Cancel отправлен, ACK нет | Нет гарантии прекращения | Late events допустимы; новые dispatch отменённого действия запрещены |
| Диагностический файл заполнен | Бизнес-state может быть исправен | Drop/rotate диагностики; отдельное предупреждение без ложной task failure |
| Изменились файлы или Git | Только обычная среда | Нет обязательного host recovery |

## Неизвестный эффект

Не создавать Host-анализатор семантической эквивалентности произвольных команд. Техническое правило узкое: автоматически не воспроизводить прежний attempt после неопределённого dispatch. Если модель предлагает повторить операцию с возможным необратимым эффектом, она должна учитывать предыдущий исход; повтор безопасен при известной идемпотентности/доказанном отсутствии эффекта либо информированном разрешении пользователя на риск. Провайдерская idempotency key используется только если контракт действительно её поддерживает.

Независимое чтение, уточнение, анализ и другой разрешённый путь не блокируются существованием unknown. Unknown не превращается в глобальное состояние «всё запрещено». Отсутствие изменений в файлах не доказывает отсутствие внешнего эффекта. Текст модели «вероятно ничего не произошло» не является наблюдением транспорта.

## Retention

`inspectFinding(operationId, ref)` показывает находку и цепочку её опор в пределах операции. Для записи с попыткой доступны outcome исходной записи и текущее состояние попытки. Инспекция показывает наличие артефакта без чтения тела, а context fetch проверяет размер и хеш при выдаче байтов.

Доверенная настройка `storage.artifactRetention` передаётся при открытии локального store. `maxAgeMs` отсчитывается от последнего записанного события операции, `maxBytes` применяется к суммарному объёму артефактов, которые можно удалить, начиная с наиболее старых. Для общего blob учитывается наиболее поздняя операция. Политика применяется при открытии под блокировкой writer. Активные операции, операции в ожидании и попытки с возможным или неизвестным эффектом защищают свои артефакты, включая общие blob. Если какой-либо снимок нельзя прочитать однозначно, проход очистки пропускается.

Снимок, находка, итог и ссылки сохраняются. При удалении опубликованного blob локальный store сохраняет маркер причины, и context fetch возвращает `unavailable` с причиной `retention`. Присутствующий blob остаётся читаемым после неудачного unlink. Повторная публикация тех же байтов восстанавливает доступ по прежним ссылкам. Экспорт диагностики по запросу редактирует секреты и не меняет рабочее состояние.

Snapshot v1 хранит целостную operation: идентичность и revision, ссылки на доверенную конфигурацию и сообщения, историю решений и допущенных действий, attempts и их ledger. Источник учёта — записи attempts. Неизвестный usage записывается как JSON null, а известный ноль — как число. Необязательные поля можно опустить. Неизвестная версия отличается от повреждённого snapshot.

Состояние хранит ссылки, а не объекты адаптера, AbortSignal, живые permission tokens или секреты конфигурации. Значения observations ограничены JSON-данными. Их поставщик отвечает за исключение секретов из полезной нагрузки.

Локальный store открывает заранее созданный каталог на локальной файловой системе с поддержкой атомарного rename, file/directory sync и межпроцессных блокировок SQLite. JSON-файл публикуется через временный файл в том же каталоге. Ошибка после rename может означать, что новая полная версия уже видна, поэтому вызывающий перечитывает snapshot. Повторное подтверждение той же revision возможно только при точном совпадении записи с сохранённой. При этом store снова синхронизирует каталог без перезаписи snapshot. В списке нет временных файлов и служебных файлов lock. Несовместимый или повреждённый snapshot не перезаписывается.

Исключительность writer реализует транзакция `BEGIN IMMEDIATE` через встроенный `node:sqlite`. SQLite-файл служит для блокировки каталога, а operation хранится в JSON. При закрытии соединения или гибели процесса блокировка освобождается. Сам lock-файл остаётся на месте, его возраст не влияет на допуск. Файловые гарантии проверены на Linux. Сетевые и иные файловые системы без этих свойств не входят в проверенную конфигурацию.

При явном resume незавершённой operation coordinator восстанавливает историю и ledger, применяет текущий доверенный grant и лимиты и запускает новый ход Controller. Завершённая operation может вернуть сохранённый ответ. Уточнение требует связанного пользовательского ответа. После restart прежние attempts без живого владельца освобождают слот, а их расход и возможные внешние эффекты сохраняются.

Опциональный `lookupStatus` относится к исходному attempt. Вызов допустим при совпадении сохранённого маршрута и доверенной конфигурации, действующем grant и negotiated capability `attempt.status`. Результат имеет provider provenance. Позднее подтверждение уточняет исход попытки, а решения предыдущего Controller из этого ответа не исполняются. Недоступная проверка статуса оставляет неопределённость видимой для модели.

Явный повтор задаётся новой action с `retryOf` и `retryBasis`. Coordinator допускает `no_effect` для известного исхода без эффекта, `user_approval` при текущем доверенном решении для этой пары attempt/action и выбранного профиля либо `provider_idempotency` с прежним ключом на том же подтверждённом маршруте. Ключ хранится только для адаптеров, заявивших `supportsIdempotency` как свой контракт. Такой адаптер отвечает за дедупликацию эффекта по ключу и отказ при изменившемся логическом запросе с тем же ключом. Конфигурация и текст модели сами по себе этих полномочий не дают. Неопределённый исход остаётся в истории и не мешает независимым действиям.

List возвращает исправные snapshots и отдельные записи `unavailable` с непрозрачной ссылкой и причиной. Имена новых snapshot-файлов содержат digest operationId и начального requestId. Поэтому повреждённое тело не позволяет повторной доставке того же начального requestId запустить новый вызов. Снимки раннего формата с digest только operationId остаются читаемыми и обновляемыми. Если такой снимок повреждён и его requestId неизвестен, новые submit отклоняются до восстановления записи, а доступные существующие операции по-прежнему можно читать и продолжать по operationId.

При чтении snapshot coordinator проверяет представление attempt ledger по упорядоченным событиям reservation, dispatch и outcome. Противоречие в собственном состоянии возвращается как corrupt_snapshot. В частности, запись о dispatch не может стать доказательством отсутствия отправки из-за изменённого статуса attempt.

## Граница применимости проверок

Результаты проверки сохраняются как исторические observations с происхождением; mutable workspace или изменение ветки не требует остановки либо перепроверки со стороны Host. Актуальность выводов — решение модели. После crash запись `unknown` означает неопределённость внешнего эффекта: не заменять её `none` из противоречивого snapshot и не выполнять blind replay. Тесты с поддельным исполнителем фиксируют этот контракт, но не доказывают его соблюдение любым нативным CLI/ACP агентом.

### Восстановление принятых Actions

Journal admissions, cancellation, reservations и outcomes определяют восстановление. Принятый, ещё не отправленный Worker может продолжиться после restart, включая локальную техническую остановку Controller; reserved/not_sent сохраняет attempt id и charge. Dispatched orphan остаётся unknown/lookup, terminal не воспроизводится. Не запускаются отменённые/отклонённые actions или действия без выполненной model-acceptance зависимости. Локальный Controller failure сохраняется; recovery не вызывает автоматический повтор Controller. Для явного продолжения Controller используется существующий user follow-up.

C12R.4: ContextPort directory metadata includes the technical unavailable reason when known. A known reference whose payload has disappeared is distinct from an oversized but present artifact; retention, missing payload, ambiguity and budget remain distinct. A legacy ambiguous reference exposes neither competing record, including positional fetch. This does not introduce a semantic retrieval or freshness gate.


## C12R.9 — непрерывность без нового хранилища

Исходная история остаётся неизменным Operation journal с observations, outputRefs, attribution, attempts, Decisions и artifact receipts; ContextPort.list/fetch продолжает читать её через действующие operation scope, authority и retention. Host формирует из этих записей ограниченную доступным контекстом техническую карту `host:invocation-context.value.workMap`: `total/represented/omitted`, исходные `actionId/attemptId`, указатель `objectiveRef` на Decision, lifecycle, dispatchCertainty, terminal/effect, outputRefs/observationRefs и capture completeness. Map не является индексом, persisted state, семантическим резюме или обещанием наличия raw bytes. Retrieval читает существующие scoped records, не запускает Actions. Missing/omitted/unavailable не устанавливают существование, отсутствие или состояние Action; Host lifecycle facts не подменяют native observations и оценку модели. Не отображённые в карте результаты остаются в исходной истории и в страницах ContextPort; завершённые попытки с `effect=unknown/possible` отдельно отмечаются в `effectUncertainties` и не трактуются как незавершённые.

Controller может *сам* запросить историю в принятом `Decision.nextController:{continue:true,contextRequest:{refs:[...],cursor?:0|{revision,index}}}`, без обязательного MCP и без нового Worker. Единственный следующий Controller invocation использует обычный разрешённый ContextPort, чтобы доставить явно выбранные refs или страницу каталога `host:history-page:0` / `host:history-page:<revision>:<index>`, с явной полнотой и причинами отсутствия; без запроса прежний путь не меняется. Внешние MCP context_list/fetch остаются опциональны. Выбор нужных refs, новых проверок и момента остановки принадлежит модели. Нет Host summarization/compaction, semantic score, принудительного replay или сохранения одной native session.

История, полученная явно по запросу, резервирует фактически занимаемое место в Controller byte budget перед необязательной технической картой. Исходные observations/provenance и ссылки не переписываются при удалении технически доказанных inline-дубликатов отображения. Literal user input остаётся обязательным, даже если превышает optional budget; при недостаточном лимите неполнота не скрывается.


### C12R.9 review — исходные результаты, достоверность и поток данных

Для финального сообщения Worker adapter (Codex CLI или ACP) может указать `ProviderResult.outputObservationRef`, если то же завершённое сообщение уже отправлено как observation данного invocation. Coordinator проверяет указанную внутреннюю ссылку, наличие её в `Outcome.outputRefs`, source/provenance, completeness и точное совпадение UTF‑8 байтов с финальным `result.output`. Только в таком случае не создаётся дополнительный `attempt-output`; оригинальные observation/outcome/ref остаются в Operation. Совпадение произвольных текстов разных sources/attempts не используется как доказательство идентичности. При отсутствии доказательства прежний `attempt-output` сохраняется.

`host:invocation-context.value.technicalCoverage` всегда содержит точные `total/represented/omitted` для `actions`, `unresolvedAttempts`, `effectUncertainties`, `cancellations`, `outcomes`, `pendingAttempts`. Нулевая длина preview при положительном `total` означает неполную доставку, не отсутствие факта. `workMap` имеет read-only `cursor/nextCursor/represented/omitted`. При необходимости Controller выбирает `nextController.contextRequest.workCursor` для другой страницы той же производной карты. Бюджет по умолчанию остаётся **256 КиБ**; режим 512 КиБ — только конфигурация для сравнительного эксперимента.

Для записи, сохранённой полностью, но превышающей лимит одной выдачи, доступен *необязательный* `ContextPort.fetch(ref, sourceOperationId?, {offset})`. Offset отсчитывается в байтах исходного UTF‑8 (или канонической JSON-представленной сохранённой value, или фактически сохранённых байтах artifact). Ответ `kind:chunk` содержит `base64`, `offset`, `totalBytes`, необязательный `nextOffset`, `format` и метаданные provenance/receipt. Нативный `context_fetch` через MCP принимает тот же `offset`; Controller без MCP может запросить `contextRequest.refs:[{ref,offset}]` в одном из следующих *обычных* вызовов. Исходные `ContextPort.list/fetch` без offset остаются совместимы. Позиционные refs `{revision,index}` действуют и в `contextRequest.refs`; не создаётся альтернативная идентичность операции. Комбинация фрагментов восстанавливает только **фактически сохранённые** байты. `artifact.truncated=true`, source completeness=truncated, retention и integrity errors остаются видимыми: несуществующий изначальный хвост восстановить нельзя.

#### Дополнение review: omission accounting и source completeness

При `contextRequest.refs` число исходно запрошенных ссылок, успешно материализованных записей и не вошедших в prompt записей различается. `historyRequestCoverage` в mandatory Host coordination metadata показывает `requestedRefs/materializedRefs/omittedDuringMaterialization` и `materializedRecords/presentedRecords/omittedDuringPresentation`, включая ситуацию, когда последний `host:history-request-budget` не помещается в optional context. Это машинные счётчики, не Host-резюме содержимого. Fragment от `offset>0` остаётся `completeness:truncated`, даже если оригинальный источник полностью сохранён; исходная сохранность отдельно показывается `sourceCompleteness`. Не считать отсутствие `nextOffset` доказательством полной доставки всего результата.

### C12R.9 review P2 — динамический предел фрагмента и стоимость чтения

`fetchMaxBytes` — доверенный **верхний предел ContextPort**, а не размер каждого фрагмента. В существующем `ContextPort.fetch(ref, sourceOperationId?, {offset, maxBytes?})` необязательное `maxBytes` означает технический предел *сериализованного ответа данного чтения*, ограниченный сверху `fetchMaxBytes`. Он не изменяет пользовательский config и не разрешает больший ответ. `materializeControllerHistory` запрашивает фрагмент с учётом Controller budget; если дополнительный model-facing envelope не помещается, byte-safe packing сохраняет максимально возможный префикс base64, уточняет `nextOffset` и отмечает частичную доставку. При недостатке места даже для metadata ответ честно остаётся `budget`. Размеры фрагментов и границы UTF‑8 не зависят от семантики содержимого.

`workMap.nextCursor` существует только при **реально доступной следующей непустой странице**. Когда последняя запись уже передана, курсор отсутствует; если при текущем байтовом бюджете нельзя уместить ни одной записи, возвращается `unavailableReason:budget` без курсора, который провоцировал бы повтор того же запроса. Устаревший/невалидный `workCursor` по-прежнему адресно помечается как `invalid_cursor`.

Для большого артефакта Local StateStore поддерживает optional `readArtifactSlice` внутри того же Artifact Store и использует ограниченный проверенный кэш (не более одного источника и 16 МиБ памяти на открытый Store). При первом чтении полный файл проверяется SHA‑256; перед каждым следующим запросом проверяются inode, размер, mtime и ctime. Смена версии файла требует новой полной проверки, отсутствие файла/retention и повреждение не подменяются содержимым кэша. Возвращаемые диапазоны копируются, чтобы внешний вызывающий код не мог изменить кэш. Кэш не долговременный, не является вторым источником истины, удаляется при close/write; альтернативный Store без оптимизации использует прежний контракт полной verified read. Дисковая нагрузка для повторных чтений неизменённого артефакта устраняется в пределах данного открытого StateStore; проверки производительности настоящих моделей остаются UNVERIFIED.

Пагинация workMap использует выданный `{revision,index}`: membership определяется исходным префиксом журнала, lifecycle и refs — текущим Operation. Порядок одинаковой admission revision сохраняет исходный admission-array index; первый Attempt занимает позицию принятого Action. `deferred` означает последнее техническое откладывание, а не окончательный запрет запуска. Новая работа доступна при новом обходе (`workCursor:0`); `liveTotal` показывает текущий размер карты. Старый числовой ненулевой offset не является устойчивым cursor и адресно возвращает `invalid_cursor`.

Accepted-only rows distinguish `accepted`, `deferred`, `rejected`, `cancelled` from authoritative execution events, including cause. A cancelled in-flight Attempt retains its actual status, `cancellation`, dispatch certainty and outcome/effect. Admission rejection of a duplicate proposal is not an execution rejection.

### C12R.9 final P2 — стабильный каталог истории

`ContextPort.list`, MCP `context_list` и `nextController.contextRequest.cursor` используют `{revision,index}` (или 0 для начала нового обхода). `revision` задаёт исходный префикс Operation journal, `index` — позицию в newest-first каталоге доступных записей этого префикса. Новые observations, Decisions, findings и Worker results не изменяют membership начатого обхода, но доступны при новом обходе. `Decision.contextCursor` остаётся ревизией контекста для Decision, `workCursor` — курсором карты Actions/Attempts, а `receivedSequence` — адресом отдельной записи, не курсором страницы. Все формы scoped к своей операции и текущим разрешениям; Worker видит только selected refs. Старые числовые ненулевые cursor декодируются для snapshot/recovery, но возвращают `invalid_cursor`, без молчаливого сброса. Схема Decision остаётся v1.

Страница содержит разрешённый `cursor`, до 32 записей и до 8192 JSON bytes; `nextCursor` указывает на следующую недоставленную запись исходного префикса. Материализация после других requested refs и окончательная Controller packing укорачивают именно структурированную страницу, не создавая текстового excerpt. Нулевой прогресс — `budget`, без nextCursor. Последняя страница не имеет nextCursor, включая пустую. Mandatory `historyRequestCoverage.directory` сообщает `kind`, `end`, `reason` при недоступности; известный invalid/closed/empty end сохраняется даже без места для optional page envelope.

Late observation может предоставить тело ранее известного output-only ref. Позиции других output refs в исходном событии не сдвигаются; старый префикс сохраняет исходный состав, а metadata разрешённой записи может отражать актуальную canonical observation и её действительный `receivedSequence`. Если ранее выданный legacy positional output-only slot мог обозначать другой ref после сдвига старого алгоритма, позиционный fetch возвращает `ambiguous` вместо потенциально чужого payload; актуальный ref или позиция canonical observation доступны через каталог. Обычные observation/Decision/finding позиции неизменны. Нет нового хранилища, semantic compaction, forced prefetch или обязательного продолжения. Стандартные независимые бюджеты неизменны.


### ACP user transcript (C15)

User-facing `session/load` follows accepted `session.requests` order, not Operation order. Exact initial Request or `operation.continued` association and optional `responseEventId` identify the historical question/assessment/status; retry returns the original response without dispatch. Durable RO facts are projected from the existing journal with recovered attribution. Background facts outside the turn boundary are explicitly attributed to their Operation; ambiguous legacy boundaries are disclosed, not guessed. Native activity and transient delivery gaps are not reconstructed. This is a user view, not model context, Observation/evidence, or a second execution journal.


C15R history fidelity: ordinary, late and conflicting outcome reports are classified against the actual prior Attempt using the existing snapshot validation ledger and shared reducer classification. This read-only pass uses historical generation/cancellation and no current limits, provider calls or intents; exact duplicates do not create a new durable report. Classification unavailable in invalid/incomplete history is disclosed with a neutral historical outcome report, not inferred from the latest terminal state. Session request order, responseEventId and stable own message IDs remain unchanged.


## C16 — последовательность пользовательских turns и восстановление Controller Decision

Первоначальный `Request.text` остаётся `Invocation.objective` для каждого Controller-вызова. `operationHistory()` содержит исходный user ContextItem и каждое `operation.continued` как отдельное исходное сообщение с `ref`, `provenance.kind=user`, `sourceId`, `receivedSequence`. `host:invocation-context.value.userTurns` публикует только ссылки `initial` и `latest` (`ref`, `receivedSequence`); тела не дублируются и не превращаются Host в synthetic active objective. `latest` означает последнюю хронологически принятую запись, а не наивысший семантический приоритет. Контекстное уплотнение сохраняет буквальные user ContextItems обязательными; optional history может быть неполной только с существующей маркировкой completeness и доступом через ContextPort. Большие исходные user сообщения сами по себе не подтверждают фактический размер доступного окну провайдера.

При `waiting:question` входящий `questionId` подтверждает связь с вопросом, но не содержание ответа. При `finished` и `waiting:technical` принятый новый `operation.continued` добавляет сообщение, не подменяя прежнее, не изменяя `Request.userConstraints` или authority и не классифицируя намерение. Пока операция `active`, C16 не вводит новый механизм доставки сообщений/steering.

Каждая отклонённая попытка Decision записывается как `controller.invalid_proposal` с `FieldError`, `attemptId` и optional технической категорией уровня parser (`invalid_json`, `non_object`, `depth`), decoder (`schema_invalid`), admission (`admission_invalid`). Никакого parsing/repair натурального model output или записи полного rejected body не добавлено. `host:decision-error` сообщает немедленную correction с техническими path/expected, категорией и derived счётчиками; `host:invocation-context.value.decisionRecovery.lastRejection` также показывает последнюю сохраняемую историческую причину после нового input, явно маркируя `prior_user_turn`. Историческая ошибка не становится новой ошибкой пользовательского сообщения. `lastRejection.active` различает активную коррекцию и исторический отказ в том же turn после принятого Decision. Активный `host:decision-error` сообщает ссылку исходного коррелированного результата, вид представления, сохранённую completeness, отдельно inline-доступность и ограниченную возможность добровольного contextRequest (MCP зависит от адаптера). Body остаётся в исходной записи; ссылка не гарантирует полные wire bytes. Метаданные коррекции учитываются в техническом бюджете, после явно запрошенных refs и запрошенной model workMap page (включая cursor 0) коррелированная запись получает место до обычных необязательных previews. Используется фактическая bounded representation из существующего общего бюджета, без новой квоты; когда возможны excerpt и минимальная адресная workMap identity одновременно, сохраняются обе. Отбор по бюджету отделён от представления: обычные выбранные записи остаются в исходном порядке journal revision/index; requested pages/chunks сохраняют отдельную проекцию. Если исходная запись уже явно материализована, она не резервируется повторно.

Из единственного Operation journal вычисляются `totalRejected` и `consecutiveIdentical` для периода после последнего `operation.continued`. Подпись ошибки = категория + `FieldError.code/path/expected`; одинаковый `attemptId` не учитывается повторно. Новая категория/ошибка либо `controller.responded` сбрасывает серию, но не суммарный счётчик. На 5-м одинаковом подряд или 10-м суммарном отклонении после durable rejection выполняется существующий переход в `waiting(kind=technical)` с `INVALID_PROPOSAL`, `resource=controller_decision_recovery` и Controller `attemptId===actionId`. Перед новой Controller reservation повторная проверка порога закрывает crash-gap между отказом и waiting. Plain technical recovery не сбрасывает счётчики; только новый принятый user turn начинает новый период. Общий `maxInvocations` никогда не пополняется. Отказы провайдера, отмены, transport errors и native tool calls не считаются отклонёнными Decisions.

Технический отказ Controller не отменяет и не переигрывает принятые независимые Workers. Продолжают действовать `controllerFailureWaiting()`, lifecycle/late outcomes, authority, cancellation provenance, CAS и unknown-effect защита. Не вводятся второй планировщик, обязательный review, искусственное workspace, Host Catalog gate для provider-native tools/skills/subagents или семантическое определение смены задачи Host.

## C18 — Intent proposals are not durable admissions

Only the selected completed Controller declaration may reach `controller.responded` after the original `attempt.outcome`; MCP submissions are invocation-local and discarded at close. An observed invalid replacement of a known proposal lineage cannot silently resurrect its earlier candidate. Unobserved client-side MCP failures are not guessed from provider text or reasoning. The selected proposal is separately attributed as a model claim, not as the final native text or a tool effect. Legacy C16 correction counters remain derived exclusively from durable **final** `controller.invalid_proposal` events (5 consecutive identical / 10 total per accepted user turn); invalid intermediate MCP submissions are not journal rejections. On cancellation/ambiguous result/resource loss no pending proposal is admitted and no unknown-effect provider call is blindly replayed. Exact crash-gap and cross-session safety remain subject to the C18 fault/restart acceptance matrix; a hashed `decisionId` alone is not receipt idempotency.

### C18R — Correlated receipt and crash-gap correction

`controller.responded` is idempotent only for the same durable Controller attempt, Decision identity and matching canonical bytes/data. Conflicting identity/content or an attempt mismatch is a technical `IDENTITY_CONFLICT`; an otherwise well-formed Decision is not labeled a model schema violation. Admission and Accepted Worker execution still derive from the **single** Operation journal. The tests distinguish lost acknowledgement before `controller.responded` (no assumed reprocessing), after an actually durable `controller.responded` (no second acceptance) and before Worker reservation/dispatch (existing restart path). A previously dispatched unknown-effect Worker remains unknown/recoverable, never blindly repeated.

Incomplete native agent messages caused by aggregate ACP capture limit remain marked through their provenance and limit observation. A distinct complete MCP submission is a model claim, not proof of execution or a reconstruction of missing native events; it can survive the capture gap only after proven normal native completion. No additional durable pending log is added.

## C18N — Transient current-invocation evidence versus committed history

Accepted current-invocation observations already have canonical operation/attempt/provider-local IDs assigned by `providerEvidenceRef`. A borrowed `LiveEvidencePort` now projects their metadata and bounded byte content through optional MCP discovery **before** an `attempt.outcome` journal commit. It shares the existing observation array, preserves actual provenance and completeness, makes no claim of exhaustive native execution and creates no second journal or observation from a discovery call. On provider detach/abort the live scope closes; any pending late outcome follows existing attribution, cancellation and durable commit rules. A live ref's identity remains the same when its original report is committed, but the early projection is not a promise of durability.

The historical `ContextPort` and its stable `{revision,index}` journal-prefix traversal remain unchanged. A new Controller invocation can address earlier declared results/rejected-result provenance using existing optional history, not the previous native invocation's `proposalRef`. Reference warnings from bounded preflight are snapshot observations only; a Worker or native event received after that warning may be considered by the authoritative admission. No mandatory retrieval, revision freshness test or Host semantic evidence scoring is introduced.

### C18N-R — Incremental advisory identity lookup

The Controller's technical preflight maintains an invocation-lifetime, monotonically extended lookup of accepted observation IDs and unreserved provider-local aliases, backed by the **same** original observation array. Historical reference sets are built once from the existing Operation event snapshot. Only references touched by the current decoded Intent are projected into the temporary `EvidenceRefs` consumed by the mutating `admitFindings` validator; shared reference identities are never mutated by that validator. This index has no payload copies, no durable writer, no freshness/relevance interpretation and is released with its invocation. A later independent Worker outcome may become authoritative after a preflight snapshot, which is why preflight remains optional and non-gating.


## C19 — Native observation metadata

An optional `native` record on a provider-attributed Observation snapshots fields reported by the current native event: `eventKind`, `nativeToolCallId`, `title`, `kind`, `status`, where actually supplied. C21 permits `title` and `kind` inherited from an earlier attributable report of the same call in the existing invocation-scoped adapter state. `native.inheritedFields` identifies exactly which retained values came from earlier reports, not the current event. An explicit clear does not inherit; missing or unreliable identity does not justify enrichment. No inheritance of status, result, exit, or payload; no synthetic status, backfill, semantic classification or new store. Projection keeps each inherited value and its attribution together or omits the value through the existing bounded mechanism. Each received string is kept unchanged up to 1024 UTF-16 code units; invalid/oversized optional fields are named in receiver-owned `native.omittedFields`, without changing capture completeness or original body. Optional metadata availability is not part of pre-existing provider-ref payload equality; the first accepted snapshot is retained without later mutation. The live and historical directories project available fields after existing metadata, within existing byte limits. `omittedMetadataFields` names omitted fields or the whole `native` record; if even that marker cannot fit at an exact byte boundary, the original accessible representation takes priority. Absence of the metadata or of an omission marker is therefore not proof that a provider omitted the field. The whole snapshot is tried before per-field omission labels. Live directory retains its existing 160-byte reservation for omission labels; historical directory uses its existing 1024-byte row bound, and an extreme exact-size row may have no spare bytes for a label. Controller and Worker handoff use the same bounded ContextItem projection: when the pre-C19 body/excerpt fills its budget, metadata may be omitted without a marker. Historical byte-chunk fetch preserves the raw bytes the original envelope could deliver, including at a saturated response budget; additional native fields and labels use only spare bytes. Historical positional fetch decides fallback from the original record size without the optional native record. Existing access, cursors, canonical identity and durable observations are unchanged. Capture completeness is independent of provider-reported tool status, directory coverage and payload availability. Live directory rows additionally carry optional `hasCapturedValue` when there is spare item budget: this indicates existence of an accepted value, not successful access, source completeness or future availability. Omission of this optional indicator means no displayed fact, not false. Fetch chunks describe saved bytes only; an exhausted page or chunk does not prove exhaustive history or full source capture. No mandatory retrieval or evidence ranking.


### C20 — Indefinite invocation and recovery

Status lookup may wait indefinitely when the provider does not reply; explicit user/shutdown cancellation races the existing lookup even if the provider ignores its signal. No independent recovery deadline, watchdog, automatic replay or new lifecycle owner. Persisted finite cumulative and concurrent limits cannot be enlarged by new defaults, even if a project preference narrows the new default. Explicit trusted user/launch reconfiguration retains the existing resume authority semantics. Existing unknown effects are not reclassified as none merely because the operator cancelled a lookup.

### C20-R capture boundary

History omission does not prevent delivery of an independently complete ACP current message. Existing observations retain their identity and completeness, no reconstruction of omitted tools. The application `captureMaxBytes` bounds artifact capture by ContextPort; ordinary provider-result acceptance is not a cumulative history-byte gate. Context projections remain bounded and retrieval optional. An incomplete anonymous current message cannot be reconstructed from later suffixes; only an existing proven native boundary permits reset.

## C22 — Correction and retrieval information

A technical correction states the prior actual failure (including missing/conflicting proposal) and follows the current invocation's rendered delivery instructions. Ordinary native final text is not a submitted Intent or Assessment. No new result reference, capture, ranking or automatic reuse. The existing rejection journal may retain optional bounded allowedFields or an alternative-form hint; older v1 records without them remain valid. Recovery identity remains [category, code, path, expected], not optional diagnostic detail; thresholds, invocation counts and user-turn boundaries are unchanged.

Historical context_fetch maxBytes limits a range response only with offset, and sourceOperationId remains subject to existing trusted sharing scope. Current-invocation evidence_fetch maxBytes limits saved bytes and defaults to offset 0 when supplied alone. These are existing distinct contracts, clarified in own tool descriptions, not new fetch behavior.
