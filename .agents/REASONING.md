# Reasoning-контракт coding-агента

Применять при реализации этого нового продукта. Эти правила улучшают решения разработчика; не превращать их в runtime-механизмы, обязательные роли, JSON-поля, evidence gates или дополнительную цепочку подтверждений пользователя.

## Обязательные качества

1. **Проверяемость.** Существенный вывод связан с конкретным контрактом, кодом или фактически выполненной проверкой. Уверенный текст не заменяет основание.
2. **Калибровка.** OBSERVED — воспроизведено/измерено; SUPPORTED — следует из конкретных исходников и семантики; HYPOTHESIS — правдоподобно; UNVERIFIED — необходимая проверка не выполнена. Не придумывать численные confidence.
3. **Причинность.** При неоднозначном сбое проверить альтернативную причину, которая меняет исправление. Выбрать различающее наблюдение вместо повторения широкой диагностики без новой гипотезы.
4. **Семантическая общность.** Выделять реально самостоятельный механизм, даже если потребитель один. Не обобщать по случайному сходству кода и не добавлять гипотетические расширения.
5. **Владение.** Для каждого состояния и ресурса назвать источник истины, писателя/владельца, время жизни и cleanup при partial failure/cancel.
6. **Направление знания.** Нижний слой не знает конкретный UI, провайдера или стратегию задачи. Поведение размещается у владельца необходимых знаний.
7. **Простота.** Минимизировать независимые истины, синхронизацию и специальные случаи. Малое число строк не является самостоятельной целью.
8. **Критичность.** Проверять фактическую реализацию, а не обещание плана. Не скрывать подтверждённые серьёзные дефекты; не выдавать stylistic preference за блокирующий дефект.
9. **Дисциплина scope.** Найти проблему можно вне текущего шага; исправлять её можно только в согласованном scope. Не подавлять finding из-за его расположения и не расширять полномочия ради зелёного теста.
10. **Непрерывность.** Доводить шаг до работающего результата и следующего ясно указанного шага. Не заменять реализацию бесконечным уточнением плана или созданием отчётов.

## Компактный цикл разработки

До существенного изменения: задача -> наблюдаемое поведение -> владелец -> контракты/риски -> минимальное решение -> проверка. После: попытаться опровергнуть решение, проверить failure/lifecycle, назвать ограничения. Это инженерный checklist, не автоматическая state machine продукта.

В greenfield отсутствие кода — нормальное исходное условие. «Найти ближайшую абстракцию» означает inspect текущего checkout и спецификации. Не обращаться к чужим историческим реализациям. Не выдумывать механизм только ради заполнения engineering frame.
